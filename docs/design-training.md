# 筋トレ機能 設計メモ

BodyMake に「筋トレの記録」と「挙上重量の推移」を足すための設計。実装前の合意事項。
README の「設計上の判断」「計算の定義」に昇格させる項目は §10 に分けてある。
検討の過程で撤回した案は §11 に理由つきで残してある（蒸し返さないため）。

---

## 1. 背骨

> **観測（測る）と行動（やる）を別レイヤーで持ち、同じ週グリッド上に並置して読ませる。
> アプリは指示をしない。褒めもしない。事実を、価値判断を乗せずに可視化する。**

いまの BodyMake は「結果（体重・体組成）→ 逆算した原因（推定カロリー収支）」という構造をしている。
筋トレログを入れると、初めて **実測された原因** が手に入る。これが拡張の価値であり、
「除脂肪体重を保てているか」を行動側から裏取りするための計測器を1つ増やす、というのが目的。

**トレーニングログアプリを作る改修ではない。** この線引きが機能の取捨選択すべての根拠になる。

### 1.1 指示をしない

BodyMake は一度も「今日は1,800kcalにしろ」と言っていない。記録し、傾向を出し、
到達予測を添える。到達予測すら記録からの導出であって指示ではない。筋トレ側も同じ性格にする。

| | 計画型（採らない） | 実績記録型（採用） |
| --- | --- | --- |
| 何と比べるか | 今日の計画 | **前回の自分 / 開始時の自分 / 体重比の自分** |
| 起きること | 達成 or **未達** | 前進 or 現状維持 |
| 未達が続くと | 開かなくなる | **そもそも未達という状態がない** |

負荷決定の支援は「指示」ではなく **事実の提示** で行う（§6.4）。

### 1.2 褒めない

2ターン目の要件は「成長を喜べる仕組み」だったが、**喜ぶ主体はユーザー**であって、
アプリが褒めることではない。むしろ事実がはっきり見えることが喜べる条件で、
アプリが感情を代行すると褒められた側の判断が鈍る。

- 入れない — Toast の祝福、🎉、「自己ベスト！」などの**演出**
- 入れる — 「過去最大」列を並べる、系列の最大点を強調する、差分の符号と数値を出す

バッジは既存の器を使うが、**成果ではなく継続にだけ足す**（§6.3）。

### 1.3 指標にしてよい値

> **ユーザーが意識して入れた値だけを指標にする。アプリが暗黙に推測した値を指標にしない。**

既存アプリはこれを守っている（体重も体脂肪率も記録日も、すべて明示的な入力）。
§11-2（自動タイムスタンプの撤回）の直接の根拠。

「入力済みの値を並べ替えて役割を判定する」（§4.2）はこれに抵触しない。
存在しないデータを作っていないし、画面に見えていて手で覆せる。

## 2. データモデル

`AppData` を version 2 に上げ、既存の `entries`（観測レイヤー）は**一切触らずに**兄弟キーを2つ足す。
`Settings` は無改変。

```ts
export type MuscleGroup = 'chest' | 'back' | 'legs' | 'shoulders' | 'arms' | 'core';

/**
 * 記録した重量をどう数えるか。器具の名前ではなく、見れば分かる持ち方を選ばせる。
 * 「ダンベルなら一律 2 倍」ではない（片手ずつのロウや両手で 1 つ持つ種目は 1 倍）。
 */
export type LoadMode = 'standard' | 'perSide' | 'bodyweight';

/** 2 つ目の入力欄の単位。挙上量は重量 × レップ数なので、秒で数える種目は計上しない */
export type RepUnit = 'reps' | 'seconds';

export type GoalType = 'weight' | 'reps';
export interface ExerciseTarget { type: GoalType; value: number }

export interface Exercise {
  id: string;                       // 生成後は不変。ログはこれを参照する
  name: string;
  group: MuscleGroup;               // 部位別の配分の分解軸
  loadMode: LoadMode;               // 挙上量と推定1RM の換算方法
  repUnit: RepUnit;                 // 回で数えるか秒で数えるか
  /** 自重種目で体重の何割が乗るか（懸垂 1.0 / 腕立て 0.65 など） */
  bodyweightFactor: number | null;
  /** 1RM 換算の分母 d。`w × (1 + reps / d)` */
  rmDivisor: number;
  /** 任意の目標。重量で決めるか回数（秒数）で決めるかを種目ごとに選ぶ */
  goal: ExerciseTarget | null;
  order: number;
}

export interface WorkSet {
  /** kg。自重種目では追加重量。perSide なら片手ぶんの値 */
  weight: number | null;
  reps: number | null;
}

export interface SessionExercise {
  exerciseId: string;
  /** 順序が意味を持つ（トップセットの判定）ため、並びを保って保存する */
  sets: WorkSet[];
}

/** キーは 'YYYY-MM-DD'（entries と同じローカル日付）。同一種目は 1 日 1 エントリ */
export type Workouts = Record<string, SessionExercise[]>;

export interface AppData {
  version: 2;
  settings: Settings;      // 無改変
  entries: Entries;        // 観測レイヤー（無改変）
  exercises: Exercise[];
  workouts: Workouts;      // 行動レイヤー
}
```

### 2.1 設計判断

**セッションという概念を持たない。** 日付キーに揃える。既存 `entries` と同じキー空間になるので、
週次集計での結合が `Map` 1本で済む。1日2部練は `SessionExercise` を並べれば表現できる。
**開始・終了時刻も持たない**（§11-2）。

**種目の削除は、その種目の記録ごと消す。**
種目だけ消してログを残すと、`sanitizeWorkouts` が参照先のないログとして黙って落とす。
つまり「残す」選択肢は実際には存在せず、**見えないところで消えるか、見えるところで消えるか**の違いしかない。
削除時に「記録 12日ぶんも一緒に消えます」と件数を出して、後者にする。

**そのうえで「非表示」を持つ（`Exercise.hidden`）。** 削除しか無かった頃は、
やらなくなった種目を候補から外すことが、その種目の推移を捨てることと同義だった。
種目マスタに残っている以上ログは宙に浮かないので、**隠しても記録は落ちない**
（アーカイブを撤回したときの前提と、ここが違う／§11-16）。

外れるのは **これから組む場面** だけ。過去を読む場面には出したままにする。

| 出さない（これから選ぶ） | 出す（すでに決まったもの・過去） |
| --- | --- |
| 記録画面の種目選び | その日のカード・記録一覧 |
| プリセットに足す候補 | 保存済みプリセットの中身（§2.2 掃除で消さない） |
| 種目の目標を追加 / 目標一覧 | 種目別の推移（記録のある種目はすべて） |
| | マイ種目の「非表示」欄（戻す場所） |

カタログでは**まだ持っていない扱い**にして出す。選び直したら表示に戻る
（`addExercises`）。「追加済み」と伏せると、押しても何も起きないボタンになり、
戻す道がマイ種目の非表示欄しか無くなる。
その日にすでに入っている種目は、非表示でも候補に残す（そこで外せないと詰む）。

改名は自由。ログは ID を参照しているので、名前を変えても履歴は分断されない。

**`perSide` は看板機能の正しさに直結する。** ダンベル種目を「20kg」と記録したとき、
実際には片手 20kg × 2 = 40kg 挙げている。バーベルやマシンは合計表記なので、
区別しないと**挙上量が種目によって2倍ずれる**。

**セットごとに weight を持つ。** `60 → 80 → 100 → 120 → 90 → 90` のような
ランプアップ〜トップセット〜バックオフの構成が、追加の型なしでそのまま入る。

**同一種目は1日1エントリ。** 同じ `exerciseId` を `SessionExercise[]` に重複させない。
朝と夜に分けてやった場合も、あとから同じ種目カードを開いてセットを足す（**再編集は自由**）。
状態が1つに保たれ、役割の導出（§4.2）が1つの並びに対して閉じる。

**`targetWeight` は `Exercise` に置く。** 既存の目標は `Settings`（体重・体脂肪率）にあるが、
種目の目標は種目に属する。目標を持つかどうかは任意。

**`step` は入力ステッパーの刻みであって、漸進のルールではない。**
最小プレートが 1.25kg か 2.5kg か、ダンベルが 1kg 刻みか 2.5kg 刻みかで正解が変わる。
理論からは決まらないので種目ごとの数値として持つ（既定 2.5）。

### 有酸素は部位ではない

`MuscleGroup` に 7 つ目を足さず、**`ExerciseGroup = MuscleGroup | 'cardio'` を別に作る。**
部位別セット数・週の配分・ヒートマップ・回復はどれも `Record<MuscleGroup, …>` のままにしておく。
1 つの enum にまとめると、それらの集計に有酸素が自動で流れ込む。
分けておけば、**部位として読んでいる箇所をコンパイラが炙り出す。**

記録する 2 つの欄は 距離(km) と 時間(分)。入力欄は増やさない。
セットはもともと「数値 2 つ」で、意味を決めているのは種目のほう（`repUnit` が秒なら重量欄は畳む）。
保存形も変わらないので移行も要らない。**意味は種目に書いてある**ので、
キーから推測する形にはしない（§11-16 の教訓）。

対応はこう置く。左右で向きが揃うようにしてある。

| 筋トレ | 有酸素 |
| --- | --- |
| `WorkSet { weight, reps }` | `CardioSet { meters, seconds }` |
| 有効重量 (kg) | 距離 (m) |
| レップ数 / 秒 | 時間 (秒 保存 / 分 表示) |
| 挙上量 = 重量 × レップ | 合計距離 = Σ距離 |
| 推定1RM（強度） | 速度 (m/分) = Σ距離 ÷ Σ時間 |

**強度はペース（分/km）ではなく速度（m/分）で持つ。**
ペースは小さいほど良い値なので、自己最高・到達率・停滞判定・グラフの向きが
その指標だけ反転する。速度なら全部「大きいほど良い」で揃い、反転が 1 か所も要らない。

読む場所だけペース表記にすることも一度試したが、**同じ事実が 2 つの単位で出る**ことになり、
記録カードと推移グラフを並べたときに読み替えが要る。単位は 1 つに揃える。

**速度はセットごとの平均ではなく 合計 ÷ 合計。**
400m×5分 と 1.6km×8分 をセット平均すると 8.4km/h になるが、
実際に動いたのは 2.0km / 13分 = 9.23km/h。短い 1 本が同じ重みで効いてはいけない。

距離は任意。縄跳びやステアクライマーには距離がないので、時間だけで扱い、速度は出さない
（推定1RM を 2〜12 レップのときだけ出すのと同じ考え方で、**無い値を埋めない**）。

出す場所と出さない場所を分ける。

| 出す | 出さない |
| --- | --- |
| 記録画面・カタログ・プリセット | 部位別セット数 / 週の配分 / ヒートマップ |
| 種目の推移（距離・時間・速度） | 部位の回復（筋肥大の回復モデルは当てはまらない） |
| 種目の目標（距離 / 時間 / 速度 / 維持） | 部位目標（週のセット数） |
| 実施日数・連続記録（走った日はトレーニングした日） | レビューの軸荷重 |
| 目標画面の「有酸素」行（今週の回数と時間） | 種目をまたいだ距離の合計 |

最後の行が要点。走った 10km と漕いだ 30km を足した「40km」に読み方はない（§11-18）。
足せるのは回数と時間まで。距離と速度は種目ごとの話なので、種目の詳細ダイアログが持つ。

**種目を分ける基準は「速度が同じ物差しに乗るか」。**

器具でも部位でもない。クロールと平泳ぎは 1.5 倍ほど速度が違うので、
1 つの「水泳」にまとめると、速度の推移が「その日どちらを多くやったか」で上下して
伸びが読めなくなる。挙上量にベンチとフライを混ぜるのと同じこと。
→ 水泳はクロール / 平泳ぎ / 背泳ぎ / バタフライに分け、**水中ウォーキング**は別に置く。
→ 自転車も屋外（実距離・25km/h 前後）とエアロバイク（機種が抵抗と回転数から出す推定距離）に分ける。
   機種が変わればエアロバイク側の値は揃わないが、**種目をまたいで比べない**ので自分の推移としては読める。

**有酸素の 1 行は「セット」ではなく「本」。**
インターバルの 400m×5本、サーキットのラウンド数がそのまま本数になる
（部位別セット数には入らないので、数え方が衝突することもない）。

**ただし 1 本のときは数を出さない。**ランニングはふつう通しで 1 回走るもので、
そこで知りたいのは「どれだけ走ったか」。「1 本」は読むものが増えるだけになる。
分けて打ったときだけ、本数そのものが量として意味を持つ。

### 繰り返す種目か、1 回で完結する種目か

**`Exercise.repeated` として持ち、既定はカタログが決める。**

行を足すボタン・連番・行の × は、どれも「何本目か」を扱うための道具立て。
通しで 1 回走る種目にそれを並べると、**入力欄 2 つで済む記録に器が 3 つ余る。**
偽なら記録画面から消えて、残るのは入力欄だけになる。

| 既定 | 種目 |
| --- | --- |
| 繰り返す | 筋トレ全部 / 水泳（25m×20本）/ 縄跳び / サーキット（ラウンド） |
| 1 回で完結 | ランニング / ウォーキング / サイクリング / ローイング / エリプティカル / ステアクライマー / 水中ウォーキング |

**種目ごとに設定から変えられる。**走る人がインターバルもやるので、
カタログの既定を動かせない値にはしない。

逆に、**歩き方のバリエーション（前・横・後ろ・もも上げ）は種目にしない。**
1 回の中で混ぜてやるもので距離も測りにくく、分けると 1 回の記録に 4 種目を並べることになる。
そのうえ入るのは時間だけで、種目ごとの数字が育たない。

名前に「水泳」を残してあるのは、絞り込みの検索が名前で照合するため
（「水泳」と打てば泳法がぜんぶ出る）。

消費カロリーは出さない（§12）。既存のカロリー収支は体重変化からの逆算なので、
運動側から足すと二重計上になる。

### ＋ ボタンは動かせる

記録画面の ＋（種目を追加）は固定位置に浮いているので、**読みたい行や指の下を塞ぐ**ことがある。
押したまま動かすと置き場所を変えられる。

離したら左右どちらかの端に寄せる。自由な位置に留めると、画面の真ん中にボタンが浮いたまま
戻せなくなる。**縦だけ覚える**（片手で届く高さは人によって違う）。

置き場所は `AppData` に混ぜず、別のキー（`bodymake.fab.v1`）で持つ。
書き出した JSON を別の端末で読んだときに、その端末のボタンまで動く理由がない。
動かしていないあいだはインラインの座標を持たないので、画面幅や safe-area の変化には
CSS 側がそのまま追従する。

### 2.2 削除の作法

**掃除で消さない。消えるのは、その操作で消してと言われたものだけ。**

| 操作 | 消えるもの |
| --- | --- |
| セット行の × | その行だけ。0 本になっても種目はその日に残る |
| 種目カードの × | その種目（入力済みのセットがあれば確認してから） |
| 目標の「目標を外す」 | その種目の目標 |

値の空いたセット・セットが 0 本の種目・値が 1 つも入っていない日は、**そのまま残す。**
空欄は「まだ打っていない」であって「消してよい」ではない。
入力欄を一度クリアするのは打ち直すときの普通の手順で、そこで器ごと落とすと
いま編集しているものが手元から消える（目標の欄なら、目標を持つ種目でなくなって行ごと消える）。

読み込み時のサニタイズも同じ。直すのは**値だけ**で、値域外は null に潰すが行や種目は落とさない。
掃くと「種目を並べて閉じた日が、開き直すと空になっている」ことが起きる。

**数えないことと消すことは別。** 実績に数えないのは `buildSessions` の仕事で、
値が 1 つも入っていないエントリはそこで外れる（§4.2）。
分けておけば、記録に出さないまま入力の途中を保てる。

### 一括削除は2系統

設定画面の削除を2つに分ける。**種目マスタは記録ではなくマスタ**なので、
`settings` を残すのと同じ理屈で、実績削除では触らない。

| 操作 | 消すもの | 残すもの |
| --- | --- | --- |
| **実績データを削除** | `entries` / `workouts` | `exercises` / `settings` |
| **すべて削除** | `entries` / `workouts` / `exercises` | `settings`（身長・目標・テーマは記録ではない） |

`useBodyData` の `clearAll()` を `clearRecords()` / `clearAll()` の2つに分ける。
「すべて削除」で消した種目マスタは、カタログから入れ直せる（§3 の復元の3経路）。

## 3. 種目カタログ

**カタログは localStorage に投入する初期データではない。** コード内の不変の定数として常に存在し、
ユーザーが選んだものだけが `exercises` に入る。**体重側の seed（`seed.ts` / `SEEDED_KEY`）とは別物**で、種目カタログは
「一度消したら復活させない」フラグを持たない。消したものは `exercises` から消えるだけで、
カタログには残り続けるので、いつでも入れ直せる。

### 初期状態は空

**初期状態は「何も追加されていない」。** カタログは選択肢の一覧であって、初期データではない。
自分がやる種目だけを選んで入れる。

| 状況 | 戻し方 |
| --- | --- |
| カタログ由来の種目を消した | 種目管理の「＋ 種目を追加」から選び直す |
| 自作した種目まで戻したい | **JSON インポート**。カタログにない種目を復元できる唯一の経路 |

カタログ由来の種目は**固定 ID**（`ex_bench` など）なので、削除して入れ直しても
過去ログの `exerciseId` 参照がそのまま繋がる。固定 ID にした理由がここにある。
自作種目は `crypto.randomUUID()` なので、この保証はない（バックアップが唯一の担保）。

**6部位すべてが埋まる構成で、計35種を収録する。** コード内定数なのでバンドルサイズは
問題にならない（数KB）。問題になるのは選ぶ負荷のほうなので、
検索 UI なしにスクロールで選べる範囲に留める。

カタログから選んだ時点で `exercises` に登録され、以後は記録画面の候補に出る。
ユーザーが意識する操作は「種目を追加」の1つだけで、登録という概念は表に出さない。

**ユーザーが決めるのは、カタログにない種目を自作したときの2択
（コンパウンド／アイソレーション）だけ。** `mechanic` は成長の主指標を切り替える
唯一の入力なので、ここだけは聞く必要がある。

### 収録リスト

種目の性質は 4 つだけ持つ。**作成時に聞くのは「見れば分かる事実」だけ**で、
数値の校正（体重係数・1RM分母）は既定値で始めて後から直す。

| 種目 | 部位 | 負荷の数え方 | 単位 | 係数 | 1RM分母 |
| --- | --- | --- | --- | --- | --- |
| ベンチプレス | 胸 | 挙上ウエイト | 回 | – | 40 |

## 4. 計算の定義

### 4.1 有効重量とセット挙上量

```
有効重量 =
  standard  : 記録した重量
  perSide   : 記録した重量 × 2   ← 左右に 1 つずつ持つ種目
  bodyweight: その日の体重（欠測なら7日移動平均）× 係数 + 記録した重量

セット挙上量 = 有効重量 × レップ数
```

**`perSide` は「ダンベルだから」ではなく「左右に 1 つずつ持つから」。**
片手ずつのロウや両手で 1 つ持つゴブレットスクワットは `standard`。
2 倍するのは、記録が片手ぶんの数字だから——バーベルベンチ 40kg は片腕あたり約 20kg で、
ダンベル 20kg×2 と同じ負荷。記録は「40」と「20」なので、揃えるには 2 倍が要る。

**秒で数える種目は挙上量に計上しない。** 挙上量は「重量 × レップ数」であって、
秒はレップ数ではない。種目側にフラグを持たず、単位から決まる。
これにより加重プランクを 20kg×60秒 と記録しても挙上量にならない。

**有効重量を使うのは挙上量と推定1RM だけ**（＝体にかかった負荷の話）。
最大重量と目標は**記録した重量**のまま扱う（＝バーに載せた数字の話）。
混ぜると、ダンベルカールに「目標 30kg」と入れたとき有効重量 60 と比べることになり、
いつまでも到達しない。

- `weight` か `reps` が `null` のセットは **除外**（0 として数えない）。
  既存 `mean()` が欠測を分母から外すのと同じ作法
- 体重の記録が一切ない期間は自重種目の値が出せず、グラフはそこで途切れる

### 4.2 トップセット

**ウォームアップという区別を持たない。書いたセットはすべて実績として数える。**

数えたくないセットは書かなければいいだけで、記録するかしないかは人それぞれ自由でよい。
並びから「これはウォームアップだろう」と推測して集計から外すのは、
**ユーザーが入れていない判断をアプリが足す**ことになり、§1.4 の原則に反する。

導出するのはトップセットだけ。これは推測ではなく、記録された重量そのものから決まる。

| 項目 | 定義 |
| --- | --- |
| **トップセット** | 最大重量のセット。**同率ならレップ最大、それも同率なら最初のセット** |

順序規則が要るのは、ストレートセット（`60×10, 60×10, 60×11`）では 3 セットとも
最大重量に該当し、結果表とグラフが参照する「トップセット」が決まらないため。

### 4.3 推定1RM と実測1RM

```
換算するのは「トップセット」1 つだけ（§4.2）

  reps = 1        → 実測値としてそのまま採用（換算式を通さない）
  2 ≤ reps ≤ 12   → 1RM = w × (1 + reps / d)
  reps > 12       → 出さない
```

**実測1RM を換算式に通してはいけない。** `w × (1 + 1/30) = 1.033w` となり 3.3% 過大評価する。
既存アプリが「推定カロリー収支」を実測と区別しているのと同じ扱い。

### 分母 d は種目ごとに変える

動員する筋量が大きい種目ほど、同じ %1RM でも反復が伸びる。
つまり同じ「w × 10 レップ」でも、w が 1RM の何%かは種目で違う。
`d` を 1 つに固定すると、その差がそのまま誤差になる。

| 種目 | d | 10 レップでの換算 |
| --- | --- | --- |
| ベンチプレス | **40** | `w × 1.25` |
| スクワット・デッドリフト | **33.3** | `w × 1.30` |
| その他（既定 = Epley） | **30** | `w × 1.33` |

出典: [FWJ の RM 換算表](https://fwj.jp/magazine/rm/)。
ベンチが `重量 × 回数 ÷ 40 + 重量`、スクワット・デッドリフトが `÷ 33.3` として示されている。

**出典が示しているのはこの 3 種目だけなので、他は Epley の 30 のままにする。**
インクラインベンチやダンベルプレスに 40 を当てるのはこちらの推測になるので、数字を作らない。
`Exercise.rmDivisor` として持ち、種目の設定から変更できる。

出典に一次情報の記載はなく、式の名前も示されていない。
README が `7,200 kcal/kg` を「国内で一般的に使われる値」として採用しているのと同じ扱い——
**検証済みのモデルではなく、明示して使う慣習値**として扱う。

### これは何の値か

換算式は特定の種目・集団の実測に当てはめた経験式で、
「何レップできるか」と「1RM の何%か」の関係は種目でも個人でも変わる。

したがってこれは **同じ種目の推移を見るための換算値**であって、
**実際に 1 回挙げられる重量の予測ではない。種目をまたいで比べる意味もない。**
画面にもその旨を書く。
同じ種目に同じ式を当て続ける限り種目固有のズレは毎回同じ方向に乗る、という前提でだけ成立している。

### 誤差を減らすためにしていること

**① 種目ごとの分母を使う**（上記）。レップ帯をまたいだ比較の誤差が減る。

**② トップセットから換算する（全セットの最大を採らない）。**
全セットの最大を採ると、**セットを多くやった日ほど高い値が出やすい**。
ノイズを含む推定を N 個並べて最大を取れば、N が増えるほど上振れするため。
セット数はその日の予定で変わるので、これは推移を読むときの系統誤差になる。
トップセットに固定すれば出どころが 1 セットに定まり、
たいていレップ数も最小なので外挿も小さくなる。

**③ 換算元のセットを併記する。** `推定1RM 75.0 kg（60×10 から）`。
3 レップからの換算と 12 レップからの換算では外挿の大きさが違う。
どれだけ伸ばした値なのかを読み手が判断できるようにする。

**④ 12 レップを超えたら出さない。** 12 レップでも 3〜4 割の外挿になる。それ以上は扱わない。

### 採らなかった誤差対策

| 案 | 理由 |
| --- | --- |
| セット間のばらつきを誤差幅として出す | ウォームアップの区別を持たないので、ランプアップを含む日は範囲が「誤差」ではなく「ランプの形」になる |
| 出典にない種目の分母をこちらで決める | 推測した値を指標にしない（§1.4）。既定 30 のままにして、設定で変えられるようにする |
| セッション間で平滑化する | 「点＝実測」の作法を崩す。生の記録が見えなくなる |

グラフでは実測を含むセッションのマーカーの形を変え、点にはそのときのレップ数を添える
（同じ種目でもレップ帯が変わると外挿量が変わるため、その日を見分けられるようにする）。
既存 `EnergyBalanceChart` が「体重ベース＝棒／体脂肪量ベース＝灰色マーカー」で
信頼度の違う値を同居させているのと同じ手法。

### 4.4 種目の開始値

```
種目の開始値 = 最初の3セッションの主指標（§4.5）の平均
               3セッション未満のときは null（開始比を出さない）
```

初回セッション1点を基準にすると、その日たまたま調子が良かった分が以後すべての差分に乗る。
README の「**開始値を初日1点にしていない**」とまったく同じ理由で、体重の7日平均に対応する粒度を
種目では3セッションとする（週1〜2回なので2〜3週ぶん）。

### 4.5 主指標

種目の主指標は**挙上量**。挙上量が出せない種目（秒で数える種目）は**最大回数**。

以前は「コンパウンド＝推定1RM / アイソレーション＝挙上量」と種目タイプで切り替えていたが、
その分類を持つ仕事が「アイソレーションで推定1RM を隠す」ことしかなく、
自作種目のたびに考えて選ばせるコストに見合わなかった（§11-23）。
推定1RM は全種目で出せるようにして、見るかどうかは本人が決める。

### 4.6 集計

| 単位 | 内容 |
| --- | --- |
| **セッション** | 種目ごとのトップセット、1RM、挙上量、ワークセット数 |
| **日** | 総挙上量、種目数、ワークセット数、総レップ |
| **週** | 総挙上量、**部位別ワークセット数**、実施日数。週は既存 `buildWeeks()` と同じ日曜〜土曜 |

**挙上量は日次で平滑化しない。**
体重の日次データは*連続量の観測*でノイズが乗るから平滑化する。挙上量は*離散イベント*で、
0 の日は「ノイズ」ではなく「休養」という意味を持つ。移動平均を引くと休養日の情報が消え、
「週2回×高ボリューム」と「週4回×低ボリューム」が同じ線に潰れる。

さらに、筋トレの空白が「休養」なのか「記録忘れ」なのかは型でも運用でも区別できない
（体重は「測り忘れ＝欠測」と一意に決まる）。

→ **週次の合計を主単位にする。** 合計は量を保存する集計なので、休養日がどう配置されていても
週の総量は変わらない。週境界を既存の体組成週次と揃えることで、行が1対1で対応する。

**総挙上量を部位で分解しない。** 挙上量は重量に比例するので、脚と背中が厚い層になり、
肩と腕は薄い層に潰れる。腕のセット数を1.5倍にしても積み上げ棒からは読み取れず、
「どこをサボっているか」という問いに答えられない。

→ **配分は部位別のワークセット数で見る。** セット数なら脚も腕も同じスケールに乗り、
部位間の比較が初めて意味を持つ。総挙上量は分解せず、単色の確認値として置く（§6.1）。

## 5. 可視化

### 5.1 種目別の推移（主役）

伸びを見る場所。**指標を1つ選んで、その1指標だけを描く。**

```
種目   [ ベンチプレス ▾ ]
指標   [ 挙上量 ][ セット数 ][ 最大重量 ][ 推定1RM ]

132.0 kg   開始比 +12.0        60.0kg のまま 3週
▓▓▓▓▓▓▓▓░░  目標 150 kg              67%
```

| 指標 | 中身 |
| --- | --- |
| 挙上量 | 有効重量 × レップ数の合計。既定の指標 |
| セット数 | その日のセット数 |
| 最大重量 | その日いちばん重かった**記録した重量**。レップ数に左右されない |
| 推定1RM | 最大重量のセットからの換算（§4.3） |

- 秒で数える種目は重量系を出さず、**最大回数**だけになる
- 点 = 各セッションのその指標値。線 = 点を結んだもの（**平滑しない**）
- ツールチップに換算元のセット（`120×3`）を添える
- **目標線と進捗バーは「最大重量」のときだけ。** 推定1RM に目標線を引くと
  「換算値が目標を超えた＝達成」と誤読される
- 開始比（最初の3セッションの平均が基準）は期間フィルタの影響を受けない

**既存 `TimeSeriesChart` を再利用する。** 足したのは 2 つだけで、
どちらも既存の体組成グラフに影響しない追加。

| 追加 | 用途 |
| --- | --- |
| `SeriesPoint.note?: string` | ツールチップに換算元のセットを添える |
| `legend?: boolean` | 同じ量を点と線で描くので凡例を消す |

### 5.2 体組成とトレーニングは別のグラフにする

グラフタブも記録タブと同じく、セグメントで分ける。

```
[ 体組成 | トレーニング ]

■ 体組成      体重の推移 / 体脂肪率の推移 / 週平均の体組成 / 推定カロリー収支（既存のまま）
■ トレーニング  種目別の推移 / 部位別ワークセット数 / 表
```

**投入（挙上量）と結果（除脂肪体重）を同じ x 軸に並置しない。**

当初はこれを「統合アプリの目玉」として置いていた。減量中に除脂肪体重が落ちていないかを、
行動の裏取りと並べて読む——という筋書きだったが、**因果があるとは言えない**。

- 除脂肪体重はインピーダンス式の体脂肪率から出した推定値で、README 自身が
  「実データで 2 週間に 17.9%〜23.6% の幅があった」と書いているほど振れる
- 除脂肪体重を動かす要因はトレーニングだけではない（栄養・睡眠・水分・測定誤差）
- 挙上量の側も、種目構成で動く粗い量

README は「2 軸グラフは目盛りの合わせ方が任意なので、実際にはない相関が見えてしまう」として
2 軸を退けている。**上下に積む形も、同じ x 軸に並べた時点で同じ主張をしている。**
軸を分けたつもりで、同じ罠に入っていた。

### 5.3 部位別の配分（ヒートマップ）

配分を見る場所。週 × 6部位、単色の濃淡。既存 `StreakStrip`（28日記録カレンダー）と同じ視覚言語。
**セット数と挙上量を切り替えられ**、最下行に週ごとの実施日数を出す。

挙上量でも成立するのは**行ごとに正規化しているから**で、部位をまたいだ比較にはならない。
横断比較（どの部位が多いか）を挙上量でやると、重量の大きい種目に支配される（§4.6）。

### 5.4 表

全グラフに表ビューを併設する（既存 `DataTables` の作法）。色が見分けにくい環境でも値に到達できる。

### 5.5 色

新しい系列色を追加しない。既存の `--s-weight` / `--s-fat` / `--s-lean` の3色は
「色覚多様性の分離条件をライト・ダーク両モードで満たす組み合わせ」として選ばれており、
ここに色を足すとその主張が薄まる。総量は単色、ヒートマップは濃淡、種目グラフは1系列。

## 6. 事実の出し方

### 6.1 主役に置くのは「更新」、総量は確認値

総挙上量を主役にすると、種目を足す・セットを増やす方向に意識が向く。総量は増えるが、
それは強くなったのではなく回復を食い潰しているだけということがある。

- **主役** — 種目ごとの推移（挙上量 / セット数 / 最大重量 / 推定1RM）
- **確認値** — 週あたりの実施日数と部位別セット数。「今週ちゃんとやったか」を見るだけ

副次的な効き目として、**1RM 挑戦日は低レップで総挙上量が落ちる**が、
主役が種目別の推移なのでそこに現れる。総量を主役にしていたら 1RM 挑戦が損な行動に見えていた。

### 6.2 「過去最大」を並べる

更新したかどうかは、言葉で言わずに**並べれば分かる**。

| 更新の種類 | 出し方 |
| --- | --- |
| 推定1RM / 実測1RM | セッション結果表に「今回」と「過去最大」を並べる。グラフは最大点を強調 |
| セッション挙上量 | 同上 |
| 相対筋力 | 同上 |

**保存せず毎回再計算する。** 既存 `derive.ts` の「保存するのは生データだけ、指標は毎回導出」に従う。

差分の色は**既存 `deltaTone(delta, lowerIsBetter)` にそのまま乗せる。**
挙上量は `lowerIsBetter = false`、体脂肪率は `true`。方向の反転は既存の仕組みで解決済み。

### 6.3 バッジ（継続系のみ足す）

`src/lib/badges.ts` の17種は 継続10 / 成果6 / 質1 の内訳。
成果系は `🚀 −5kg` `💪 質の高い減量` のように絵文字つきで称賛的で、
**ここに「ベンチ体重の1.5倍」を足すのは §1.2 の「演出を入れない」に反する。**
一方、筋トレ側に何も出さないと、体重 −3kg は 🚀 で出てベンチ +20kg は出ない非対称が残る。

→ **継続系のみ足す。** 行為の事実であって成果の称賛ではないので §1.2 と両立する。

- 通算セッション数（30 / 100）
- 週2回以上を N 週継続
- 全部位を1週間で一巡

成果系（推定1RM の開始比、体重比マイルストーン）は足さない。
数値は §7.3 の結果表と §5.1 のグラフに出るので、到達は見れば分かる。

`computeBadges(stats)` を `computeBadges(stats, training)` に広げる。**Toast や 🎉 は足さない。**
（成果系を足す代案は §14）

### 6.4 負荷決定の支援は「事実の提示」に徹する

| 出す（事実） | 出さない（指示・問いかけ） |
| --- | --- |
| 前回 60kg×10,10,9 | 「今日は 62.5kg でやりましょう」 |
| 推定1RMの推移 | 「あなたの適正重量は◯kg」 |
| **トップセット 60kg のまま4週間** | 「重量を上げるべきです」 |

停滞の提示は**負荷を決める材料としては最も価値が高い**。しかも「4週間同じ重量」は
解釈ではなく事実なので思想に反しない。決めるのは本人、材料は全部出す。

### 6.5 種目ごとの目標

`goal` を設定すると、ホームの「種目の目標」カードと推移グラフに進捗が出る。

**重量と回数（秒数）から選べる。** 加重できる種目は重量、懸垂やプランクは回数・秒数で決めたい。
目標の種類は 2 つのままで、単位は種目の `repUnit` から決まる（回数と秒数は同じ欄の値）。

| 種類 | 現在地の測り方 |
| --- | --- |
| 重量 | その日に**記録した重量**のうち最大のもの |
| 回数（秒数） | その日の最大レップ数（秒数） |

**推定1RM では判定しない。** 「100kg 挙げたい」に対して換算値が 100 を超えたから達成、では嘘になる。
**有効重量でも判定しない。** 打った数字と同じ土俵でないと、ダンベルカールに「30kg」と入れたとき
有効重量（片手30×2=60）と比べることになり、いつまでも到達しない。

- 現在地 = 直近セッションの値
- 開始値 = 最初の 3 セッションの平均（§4.4 と同じ作法）
- 進捗 = (現在 − 開始) ÷ (目標 − 開始)。ただし **到達していれば 1**

**到達はバーより強い。** 到達したかどうかは現在地と目標だけで決まる事実で、開始値を要らない。
比率だけでバーを描くと、目標が開始値より下にあるとき（低く決め直した／決めた時点で超えていた）
分母が負になり、「到達」と出ているのにバーが空という食い違いが出る。
記録が 3 セッションに満たず開始値が出せない場合も同じ。事実の側にバーを合わせる。

**到達予測は出さない。** 体重は毎日1点だが種目は週1〜2点で、しかもプラトーする。
線形外挿が成立しない。

## 7. 画面

### 7.1 タブ

```
ホーム / グラフ / 記録 / 設定        ← タブは増やさない
                └ [ 体組成 | トレーニング ]
```

体重だけでなく体脂肪率も記録するので、名前は「体組成」にする。

**トレーニングは独立したタブにしない。** 体重もトレーニングも「その日に何をしたか」の記録で、
概念として並列。タブを増やすとアプリの性格が「体重アプリ＋筋トレアプリ」に見えてしまう。
記録タブの中でセグメント切り替えにする。日付は両者で共有するので、切り替えても同じ日を見続ける。

### 7.2 記録画面（トレタブ）

予定行を並べず、やったことが積み上がる形。

カード右上に日付を出さない。ヘッダに今日の日付があり、すぐ下に日付ナビもあるので三重になる。

```
トレーニング                        ← 右上に日付を置かない
‹  2026-03-10  ›  [今日]

ベンチプレス                    前回 60kg×10,10,9
  60 × 10
  60 × 10
  60 × 11
  ────────────────────────
  1,860kg   前回比 +60kg

[ ＋ 種目を追加 ]
```

- 空欄が並ばない。押すと1行増える
- 前回の実績は**薄く添えてあるだけ**。目標ではなく参照
- 進捗バー（`18 / 30回`）は計画に対する達成率なので**置かない**

**± ボタンは置かない。** 1 行に重量と回数を並べる都合上、ボタンを付けると数値の表示幅が削られ、
肝心の値が読みにくくなる（体重側の `NumberField` も同じ理由で ± を外した）。
直近の値はプレースホルダに薄く出して目安にする。

**前回のセット列を丸ごと複製する1タップ**が本命の動線。可変重量セッションでこそ効く。

```
ベンチプレス
  前回 (3/7):  60×5  80×3  100×2  120×3  90×10  90×9
  [ 前回の構成で始める ]        ← 6行が重量入りで入る。差分だけ直す
```

削除は §2.2 の作法に従う。各セット行の × で消す。

**体組成側にも同じことをする。** カード名を「体組成」にし、右上の日付表示を落とす。

### 7.3 記録一覧（その日の結果もここに統合する）

「この日の結果」を別カードにすると、記録一覧と同じ情報が 2 か所に出る。1 つにまとめる。

```
記録一覧                        タップで内訳

  3/10 (月)   胸・腕        3種目
    ┌ 展開 ────────────────────────────┐
    │ 種目           セット  挙上量    推定1RM │
    │ ベンチプレス      3   1,860 kg   132.0  │
    │ ダンベルフライ    3     720 kg     —    │
    │ [ この日を編集 ]                        │
    └────────────────────────────────┘
```

行に出すのは**日付・部位・種目数**だけ。展開すると種目ごとの内訳が出る。
`RecordsView.module.scss` の行スタイルを流用して、体組成側と見た目の語彙をそろえる。

**種目をまたいだ合計を出さない。** 総挙上量も、セット数・レップ数の合計も、
種目を無視すると意味を失う。スクワットの 1,500kg とサイドレイズの 900kg を足した数字は、
何が増えたのか減ったのかを説明しない。**挙上量とセット数は種目ごとに出す。**

**推定1RM は種目の記録カードと、この内訳にだけ出す。** 一覧の行には出さない。

**過去最大はここに出さない。** 比較は後から作るホームのダッシュボードとグラフの仕事で、
記録画面は「その日に何をしたか」に専念させる。

### 7.5 設定はカテゴリに集約する

1 画面に全部並べると縦に長くなる。かといって項目ごとに画面を分けると階層が深くなる。
**「何についての設定か」で切り、1 画面に複数カードを載せる。**

```

      マイ種目     一覧・追加・種目ごとの設定   12件 ›
```

（体組成の身体と目標は目標タブへ移した。§7.1）

**トレーニングの中だけ、もう 1 段ある。** 扱うものが 2 つあり、しかも数が違う。
マイ種目は数十件並ぶので、1 枚に積むとプリセットがその下に埋もれる。
段を 1 つ増やすぶんの往復より、目当てのものが**件数つきで見えている**ほうが速い。
`#settings/training/presets` のように、この段も URL に載せる。

**遷移先は URL に載せる**（`#settings/general`）。既存のタブが
「standalone 表示の戻る操作とリロードで位置が保たれる」ようにハッシュを使っているので、

**種目の一覧は 1 つ。** 目標と種目管理を別カードにすると同じ 35 行が 2 回出て縦に倍になる。

```
マイ種目                      35件 / 目標 2件
[ ＋ マイ種目に追加 ]                 ← 名前・部位・負荷の数え方・回数の単位＋[詳細設定]
```

## 9. 移行と互換

- `sanitizeData()` に v1→v2 の分岐。v1 は `exercises: []` / `workouts: {}` を補うだけ。
  既存のサニタイズ層がある強みでコストは小さい
- **保存ガードは入れない。** 現行 `sanitizeData` は未知キーを落とすので、1a をデプロイしたあと
  ロールバックすると `exercises` / `workouts` が消える（`entries` と `settings` は残る）。
  これは**許容する**。新しいビルドにガードを入れても、ガードを持たない旧ビルドの上書きは
  止められないので v1→v2 では効かず、守れるのは「将来 v3 を出したあと v2 に戻したとき」だけ。
  そのために `saveData()` を黙って no-op にするのは、記録しているのに保存されないという
  **より危ない失敗モード**を作る。復旧経路は既存の JSON エクスポートで足りる
- **復元経路は JSON 一本にする。** CSV は体組成しか運べないので、読み戻しに使えると
  思われた時点で「CSV をバックアップとして取っていたら筋トレが消えた」が起きる。
  `parseCsv` を撤去し、CSV は**書き出し専用**にした
- CSV 書き出しは残す。既存が `# 日次記録` / `# 週次分析` のセクション区切りなので、
  `# 筋トレログ` を足すだけで乗る。役割は「Excel でレポートを作るための出口」
- **`seed.ts` / `SEEDED_KEY` は残す**（デモで初見の人がグラフを見られる価値を優先）。
  ただし `loadData()` の seed 分岐が `exercises` / `workouts` を落とすので**修正が要る**。
  現行は `return { version, settings, entries: seedEntries() }` と再構築しており、
  体重0件かつ未 seed のユーザーの筋トレが消える。
  `const base = stored ?? emptyData()` を作って `{ ...base, entries: seedEntries() }` を返す形にする。
  種目カタログは localStorage に触れないので（§3）、seed の対象は体組成データだけ
- `DATA_KEY` は `bodymake.data.v1` のまま**変えない**。キー名はスキーマ版ではなく保存先の
  アドレスで、`.v2` に変えると既存ユーザーのデータが見えなくなる
- **インポートで筋トレが落ちないようにする。** `readImportFile` は `sanitizeData(raw)` で
  v2 全体を復元しているのに `ImportResult` が `entries` / `settings` しか運んでいない。
  `io.ts` / `useBodyData` / `SettingsView` の3つに手を入れる。
  エクスポートは `JSON.stringify(data)` なので無改変で通る
- `Stats` を肥大させない。`computeTrainingStats()` を別関数にし、
  バッジのために `computeBadges(stats, training)` へ引数を広げる
- **`vitest` を devDependency に足し、`src/lib` の純関数だけテストする。**
  今回の導出は既存 `derive.ts` より条件分岐が多く、しかも定義の細部がそのまま結果を変える
  （トップセットの同率規則、`warmup` の三値、開始値の3セッション、e1RM の `reps` 境界、`perSide` の ×2）。
  目視では踏まない種類の壊れ方をする。**§10 の定義表がそのままテストケースになる。**
  README の「ランタイム依存は React のみ」は devDependency では崩れない

## 10. README に昇格させる項目

### 「計算の定義」表への追加行

| 項目 | 定義 |
| --- | --- |
| 有効重量 | 片側記録は ×2。自重種目はその日の体重（欠測時は7日移動平均）× 係数 + 追加重量 |
| セット挙上量 | 有効重量 × レップ。欠測セットは除外（0 として数えない） |
| トップセット | 最大重量のセット。同率ならレップ最大、それも同率なら最初 |
| 推定1RM | トップセットを `w × (1 + reps / d)` で換算。2〜12レップのときだけ。 |
| | `d` は種目ごと（ベンチ 40 / スクワット・デッド 33.3 / 既定 30）。 |
| | 同じ種目の推移を見るための換算値で、1回挙げられる重量の予測ではない |
| 実測1RM | 1レップのワークセット。Epley を通さない（3.3% 過大になるため） |
| 相対筋力 | 推定1RM ÷ その日の体重 |
| 種目の開始値 | 最初の3セッションの主指標の平均。3セッション未満は出さない |
| 週トータル挙上量 | 週内のセット挙上量の合計。週は日曜〜土曜 |

### 「設計上の判断」への追加

1. **挙上量を日次で平滑化しない。** 体重は連続量の観測だが挙上量は離散イベントで、
   0 の日は「休養」という意味を持つ。合計は量を保存するので週次でまとめる（§4.6）
2. **総挙上量を部位で分解しない。** 挙上量は重量に比例するので脚と背中が支配し、
   肩と腕の変化が読めない。配分は部位別ワークセット数で見る（§4.6）
3. **伸びは種目ごとに見る。** 総量は「今週ちゃんとやったか」の確認値であって、
   強くなったかどうかは種目別の推移に出る（§6.1）
4. **種目には到達予測を出さない。** 体重は毎日1点だが種目は週1〜2点で、しかもプラトーする。
   線形外挿が成立しない（§6.5）
5. **アプリは指示をしない。** 負荷決定の支援は事実の提示で行う（§6.4）
6. **アプリは褒めない。** 「過去最大」を並べれば更新は見れば分かる。喜ぶのはユーザー（§1.2）
7. **重量とレップだけから引いた値であって、フォーム・睡眠・栄養・疲労は見ていない。**
   既存の「医療的・栄養学的な助言ではありません」と同じ位置に置く

注記として1行 — 同じ種目を1日に分けてやると、軽い側のセットがウォームアップと判定される。
記録画面で手で変更できる（§4.2）。

  筋トレの記録を収支に足さない理由（二重計上になる）を読者に明示する

## 11. 検討の過程で撤回した案

蒸し返さないための記録。判定基準は
**「いま生きている思想だけから再導出できるか。できないなら遺物」**。

**1. 部位別の既定値**
既定値の中間層を `MuscleGroup` にしていた。増分を決めるのは部位ではなく器具。
→ プログレッションごと消滅（6）。`MuscleGroup` は部位別セット数の分解軸としてのみ残る。

**2. セットの自動タイムスタンプと「密度」指標**
所要時間を成長軸にしようとしたが、**後日まとめて入力する人にとっては
実施時刻ではなく入力時刻を記録してしまう。** しかも「30回を12秒」のような
明らかな異常値ではなく*それらしい値*が残るので、壊れていることを検出できない
（体組成計のノイズは体重ベースと並べれば乖離が見えるぶんまだマシ）。
→ §1.4 の原則を立てて破棄。セッションに時刻を持たない設計へ戻した。
→ 「休憩を伸ばせば誰でも達成できる」という懸念も、実績記録型では判定自体がないので消滅。

**3. 「今日のメニュー表」（計画型の画面）**
提案値を入れた予定行を並べる画面を主動線にしていたが、**実績記録アプリの性格に反する。**
「未達」という状態を作り、それが積むとアプリを開かなくなる。
→ 実績が積み上がる形（§7.2）へ。

**4. 問いかけ型の設定調整提案**
「増分を上げますか？」は指示に寄る。事実の提示にとどめる（§6.4）。

**5. e1RM を第1セット限定にする案**
疲労下のセットが汚染するので第1セットのみ、としていたが、
**ランプアップ型（第1セットが 60kg のウォームアップ）で破綻する。**
「ワークセットのうち最大」を採れば疲労下の低い値は自動的に落ちる（§4.3）。

**6. プログレッションルール一式**
`progression` / `repRange` / `targetSets` / `targetReps` / `increment` /
`TrainingDefaults`（目的 × mechanic のプリセット表）/ 3層継承。
「指示をしない」と決めた時点で残った仕事が**入力欄の初期値をずらすことだけ**になり、
そのために5フィールド＋プリセット表を持つのは釣り合わない。
可変重量（ランプアップ〜バックオフ）では正しく効く場面も狭い。
→ 全削除。`increment` だけ **`step`（入力ステッパーの刻み）** に改名して残した。
→ 連動して以下も削除：
  - **`Routine`（メニュー）** — 「前回のセット列を丸ごと複製」が上位互換。
    「今日は Push の日」は計画型の語彙
  - **セット分割 PR** — 前提だった固定重量＋総レップ目標のモデルが消えた
  - **重量 PR の下限レップ条件** — `repRange` に依存していた。実測1RM を一級市民にした時点で前提が崩れていた
  - **「増分は現在重量の 4.2%」の事実表示**
→ なお5ターン目の「**休憩しながらでもやり遂げたら OK**」という発想は、
  仕組みごと消えるだけで挙動としては完全に生きる。`12, 8, 6, 4` と記録すれば合計30回として積まれ、
  未達判定も何も起きない。**目標という概念を持たないほうが、あの発想の純度は高い。**

**7. 部位別の挙上量積み上げ棒 / 押す・引く・脚の3分割**
挙上量は重量に比例するので、脚と背中が厚く肩と腕が薄い層になり、配分が読めない。
3分割案は**色が3色しかないという制約から逆算したもので、順序が逆だった**。
しかも動作パターン軸なので部位と一致しない（デッドリフトは「引く」だが実質は脚と背中）。
→ 総量は分解せず単色、配分は部位別ワークセット数のヒートマップへ（§4.6 / §5.3）。

**8. 報酬レイヤー**
PR の Toast、🎉 と「自己ベスト！」の文言、体重比マイルストーンの祝福、
「今週のハイライト」カード、累計トンの報酬扱い。
→ 全廃。「過去最大」列と最大点の強調に置き換え（§1.2 / §6.2）。
   バッジは継続系のみ既存の器に足す（§6.3）。

**9. 「差分に良し悪しの色を乗せない」という表示規則**
提案したが、**既存アプリと衝突していた。** `StatTiles` は既に
`deltaTone(delta, lowerIsBetter)` と `ui.good` / `ui.bad` で方向反転を解決している。
→ 撤回し、既存の仕組みに合わせる（§6.2）。

**10. 「種目ごとのトレンド線は出さない」**
「週1〜2点の系列に線を引くとないトレンドが見える」として除外していたが、行き過ぎだった。
問題なのは**欠測日を含む暦日軸に平滑線を引くこと**であって、
実施したセッションを点で並べて結ぶのは生データの表示。
→ **種目別の推移を主グラフに格上げ**（§5.1）。

**11. 種目グラフの「点＝実測、線＝導出」**
体重グラフの語彙をそのまま持ち込んだが、種目では点と線に*別の量*を割り当てることになる。
アイソレーションでは「点＝トップセット重量（kg）／線＝挙上量（kg·reps）」で
**同じ y 軸に載らない。** コンパウンドで単位が揃う場合でも「線は点の平滑値」と誤読される。
→ 1指標1グラフ、指標トグルで切り替える形へ（§5.1）。

**12. 種目ごとの到達予測**
`GoalMeter` と `computeProjection` を丸ごと再利用するつもりだったが、
データ密度（週1〜2点）とプラトーする性質から線形外挿が成立しない。
既存の `points.length < 4` ガードでは足りない。
→ 目標線と進捗バーのみ。予測は出さない（§6.5）。

**13. 筋トレを独立タブにする案（5タブ）**
「入力頻度が体重と同等なので1タップで届くべき」として `トレ` タブを足したが、
**トレーニングの記録は「記録」の一種**で、並列に置くほうが概念に合う。
タブを増やすと、1つのアプリではなく2つのアプリが同居しているように見える。
→ 記録タブ内のセグメントへ（§7.1）。タブは4つのまま。

**14. 入力の ± ステッパー**
既存 `NumberField` の作りをそのまま踏襲したが、
**モバイルで 1 行に重量と回数を並べると、± のぶんだけ数値の表示幅が削られる。**
実機で体重の数字が読みにくくなることが分かった。
→ 体重側・筋トレ側の両方から ± を外し、直近の値はプレースホルダで示す（§7.2）。
→ 副作用として `Exercise.step` の効き目が「PC の上下キーと数値の粒度」だけになった。
   モバイルでは実質何もしない。将来の削除候補。

**15. ウォームアップの自動判定と W トグル**
`warmup` を三値で持ち、トップセットより前の軽いセットを既定でウォームアップ扱いにして
挙上量から外していた。手で覆せることを根拠に §1.4（推測した値を指標にしない）に
抵触しないと説明していたが、**その説明は覆せる手段があってこそ成り立っていた**。
そもそも「記録するかしないかは人それぞれ自由」で、
数えたくないセットは書かなければいいだけ。書いたものを勝手に外す理由がない。
→ `WorkSet.warmup` と W ボタンを廃止。`SetRole` は `'work' | 'top'` の 2 値に縮み、
   導出は「トップセットを 1 つ決める」だけになった（§4.2）。

**20. 推定1RM を「全ワークセットの最大」で出すこと／分母を 30 に固定すること**
撤回 5 で「第 1 セット限定」をやめて「ワークセットのうち最大」にしたが、
**最大を採る方式にも系統誤差がある。** ノイズを含む推定を N 個並べて最大を取ると
N が増えるほど上振れするので、「セットを多くやった日ほど 1RM が高く出る」形で推移が歪む。
また Epley の分母 30 を全種目に当てるのも、動員筋量の違いを無視していた。
→ **トップセット 1 つから、種目ごとの分母で換算する**（§4.3）。

**26. 累計挙上量**
「絶対に下がらない報酬」として Phase 3 に積んでいたが、
**種目をまたいだ合計そのもの**で、撤回 18 と正面から矛盾する。
`SessionPoint` から集計値を削除した時点で、計算する手段もアプリ内に無くなっていた。
→ 不採用。

**25. 「挙上量に計上しない」という種目の設定**
プランクのために `loadMode: 'none'` を持っていたが、
**挙上量＝重量 × レップ数**という定義があれば「秒はレップ数ではない → 計上できない」が自動的に従う。
種目側にフラグを持つ必要がなかった。しかも `none` はフラグを立て忘れると
加重プランク 20kg×60秒 が 1,200kg として計上される作りだった。
→ `repUnit === 'seconds'` から決まる。選択肢が 4 → 3 に減った。
→ アブローラー（回数だが挙上量を出せない）も、重量を記録しなければ 0 になるので特別扱い不要。

**24. 目標を有効重量で判定すること**
ダンベルカールに「目標 30kg」と入れると、有効重量（片手30×2=60）と比較していた。
打つ数字は片手ぶんなので、60kg のダンベルを持つまで到達にならない。
→ **有効重量を使うのは挙上量と推定1RM だけ。最大重量と目標は記録した重量**（§4.1）。

**23. 種目タイプ（コンパウンド／アイソレーション）と「負荷の種類＋片手ぶんか」の分離**
`mechanic` の仕事は「アイソレーションで推定1RM を隠す」ことだけで、
自作種目のたびに考えて選ばせるコストに見合わなかった。
`loadType` と `perSide` も、2 つに分かれていると「ダンベルは片手ぶん？」を毎回考えることになる。
→ `mechanic` を廃止し、`loadType` + `perSide` を **`loadMode`（負荷の数え方）1 つ**に統合。
   選ぶのは器具の名前ではなく、見れば分かる持ち方。
   自作種目で聞くのは 名前・部位・負荷の数え方・回数の単位 の 4 つになった。
→ `Exercise.step`（入力ステッパーの刻み）も、± ボタンを外した時点で
   モバイルでは何もしていなかったので削除した。

**22. ホームに体組成の入力フォームを置くこと**
トレーニングが無かった頃の名残で、`QuickEntry` がホームと記録タブの両方に出ていた。
記録タブが体組成とトレーニングの入力を両方持つようになった時点で、
**体組成だけホームにも入力がある**という非対称になっていた。
→ ホームから外し、役割を `ホーム = 状態 / グラフ = 分析 / 記録 = 入力 / 設定 = 設定` に揃えた。
   記録が 0 件のときだけ、ホームから記録タブへ飛ぶボタンを出す。
→ コストは体重を記録するときのタップが 1 つ増えること（タブバーの「記録」を押す）。

**21. 相対筋力（推定1RM ÷ 体重）とトップセット重量の指標**
相対筋力は「体重が変われば絶対重量どうしの比較が意味を失うので正規化する」として
背骨（§1.3）に据えていたが、**指標を増やしただけの効果しかなかった。**
トップセット重量も、推定1RMがそこから換算されている以上ほぼ同じ形の線になる。
→ 両方削除。指標は `推定1RM / 挙上量 / セット数` の 3 つ。
→ `ExercisePoint.relative` も型ごと削除した。
→ 失うもの: 減量中に「体重が落ちて推定1RMが横ばい＝実質前進」を1本の線で読む手段。
   体重の推移は体組成タブにあるので、必要なら見比べる。

**19. 週トータル挙上量と除脂肪体重の上下並置**
投入と結果を同じ x 軸に並べて読ませる画面を「統合の目玉」として置いていたが、
**そこに因果があるとは言えない。** 除脂肪体重はインピーダンス式の推定値で振れが大きく、
動かす要因もトレーニングだけではない。挙上量の側も種目構成で動く粗い量。
README が 2 軸グラフを退けたのと同じ理由が、上下並置にもそのまま当てはまる。
軸を分けたつもりで、同じ「ありもしない関係を見せる」形になっていた。
→ グラフタブを `[ 体組成 | トレーニング ]` に分け、それぞれ別の指標を出す（§5.2）。
→ 連動して **`SessionPoint` から `volume` / `workSets` / `reps` を削除**した。
   種目をまたいだ合計の置き場所がアプリ内から完全に無くなったため。

**18. 種目をまたいだ合計（総挙上量・総セット数・総レップ数）**
セッション結果表の見出しに「総挙上量 4,320 kg / 9 セット / 84 レップ」を出していたが、
**種目を無視した合計は何が動いたのかを説明しない。**
スクワットの 1,500kg とサイドレイズの 900kg を足した数字に読み取れる意味がない。
セット数・レップ数も同じで、どの種目のセットかが分からなければ配分も強度も読めない。
→ 合計をやめ、**挙上量もセット数も種目ごとに出す**（§7.3）。
→ 「この日の結果」カードも廃止し、記録一覧の展開に統合した。

**16. 種目のアーカイブ（論理削除）**
物理削除すると過去ログの `exerciseId` が宙に浮くので、`archived` で隠すだけにしていた。
しかし **`sanitizeWorkouts` は参照先のないログを落とす**ので、
「種目を消してもログは残る」という前提自体が成り立っていなかった。
残っているように見えて次回の読み込みで消える、いちばん悪い形。
→ アーカイブを廃止し、**削除は記録ごと消す**（件数を出して確認する）。
   隠す・戻すという操作も、それを説明する文言も要らなくなった（§2.1）。

**（後日）非表示として戻した。** 撤回の理由は「隠してもログは残らない」だったが、
それは *種目マスタから消したとき* の話で、**マスタに残したまま隠す**なら参照先は生きている。
`sanitizeWorkouts` が落とすのは参照先のないログだけ。前提の読み違いだった。

戻す判断がついたのは、カタログが 90 種目になり、プリセットと目標が種目を参照するようになってから。
やらなくなった種目を候補から外す手段が削除しか無いと、**そのたびに推移を捨てる**ことになる。
隠す・戻すの文言は 2 行で済む（§2.1 の表）。

**17. 「すべて追加（初期状態に戻す）」**
カタログ全 35 種を入れることを「初期状態に戻す」と書いていたが、
**初期状態は空**が正しい。カタログは選択肢の一覧であって初期データではない。
→ 文言を「残り N 件をまとめて追加」に変更（§3）。

**27. 「空の器を残さない」（削除の連鎖）**
「両方 null のセット → セット 0 本の種目 → 種目 0 件の日」と落とす規則を持っていた。
体組成側の「4項目すべて空になった日はキーごと落とす」に揃えたつもりだったが、
**体組成の欄は消せば未記録に戻るだけなのに対し、こちらは器（種目）まで一緒に消える。**
セット行の × を押したら種目が消え、目標の欄をクリアしたら目標そのものが消える。
どちらもユーザーが頼んでいない削除で、しかも取り消せない。
→ 撤回。消えるのは操作で消したものだけにし、空のまま残すことを許す（§2.2）。
   実績に数えない役は `buildSessions` 側（`hasAnySet`）が持っているので、
   掃除をやめても「打つ前から実績になる」ことは起きない。

## 12. 採らないもの

| 採らない | 理由 |
| --- | --- |
| 不透明な推奨アルゴリズム | ルールが1段落で書けないものは README の説明責任を果たせない |
| RPE / RIR | 主観入力の精度に全体が依存する |
| 周期化・ブロックピリオダイゼーション | 専用アプリの領域 |
| 休憩タイマー・インターバル指示 | §11-2 と同じ。時間軸に依存しない設計にした |
| 種目ごとの日次トレンド線（暦日軸の平滑線） | 欠測日を含む軸に線を引くと、ないトレンドが見える |
| 有酸素の消費カロリー推定 | 既存のカロリー収支は**体重変化からの逆算**で一貫している。 |
| | 運動側から推定値を足すと二重計上になり、README の説明が破綻する |
| サーバー同期・SNS共有 | 「サーバーへ何も送らない」という既存の約束を壊す |
| 有酸素のペース表示（分/km） | 小さいほど良い値を 1 つ混ぜると、その指標だけ向きが反転する。表示だけ分けても、同じ事実が 2 つの単位で出る（§2.1） |
| 心拍・ゾーン | 実測できる端末を前提にできない。推測した値を指標にしない（§1.3） |

## 13. Phase

**Phase 1a — 記録できて、その日の結果が見える**
v2 移行（§9）/ `vitest` の導入 / 種目マスタとプリセット28種 /
記録画面（日付ナビ、前回セット列の複製、削除）/
セット役割の導出・有効重量・セット挙上量 / セッション結果表

> ここまでで自分で使い始められる。**実データが取れてから 1b 以降を決める**のが安全で、
> ヒートマップの正規化（§5.3）や指標の見え方（§5.1）は実物を見ないと詰めきれない。

**Phase 1b — 推移が見える**（完了）
グラフタブの `[ 体組成 | トレーニング ]` 分割 /
種目別の推移グラフ（`TimeSeriesChart` 再利用、指標トグル、目標線）/ 元データの表

> 種目セレクタは**記録のある種目だけ**を、記録数の多い順に出す。
> 指標は `推定1RM / 挙上量 / トップセット` で、既定は種目タイプごとの主指標（§4.5）。
> アイソレーションでは推定1RMを選択肢に出さない。

**Phase 2 — 読み取りを助ける**（完了）
セット数と最大重量の推移 / 種目の開始値と開始比 / 目標重量の参照線と進捗バー /
停滞の事実提示 / 部位別の配分（セット数・挙上量・実施日数）/
継続系バッジ 5 種 / `StatTiles` に「今週のトレ」

> バッジは**行為の事実だけ**を数える（通算セッション数 / 週2回をN週継続 / 全部位を一巡）。
> 挙上重量の伸びは閾値表示しない（§6.3）。

**Phase 3 — 入出力と周辺**（完了）
CSV に筋トレのセクションを追加（書き出し専用）/ README 反映

> CSV は「セット単位の明細」と「週次の部位別セット数」を足した。
> 集計済みの数字を並べるより、ピボットテーブルで好きに切れるほうがレポートの材料になる。
> 累計挙上量は不採用（§11-26）。

**将来** — CSV の先に Excel レポート生成を置く。
書き出し専用と決めたので、読み戻しの制約に縛られず列構成を変えられる。

## 14. Phase 2 で決めること

いずれも Phase 2 の実装時に決まるもので、1a / 1b の着手を止めない。
そのころには実データが貯まっている。

**バッジに成果系を足すか（§6.3）**
現状は継続系のみ採用。足すなら「推定1RM の開始比 +10 / +20kg」「体重比 1.0 / 1.5 / 2.0倍」。
足せば体重側との非対称は消えるが、既存バッジが絵文字つきの称賛表現である以上、
§1.2 の「褒めない」は文面だけになる。**Phase 1a を使ってみて、非対称が気になるかで決める。**

**種目ごとの到達予測を出すか（§6.5）**
現状は出さない。出すなら `points.length < 4` ではなく「直近8セッション以上」まで
ガードを厚くし、窓も28日より長く取る必要がある。
プラトーを外挿する問題は残るので、出すとしても「直近の傾きが続いた場合」という但し書きが要る。

**ヒートマップの濃淡の実際の見え方（§5.3）**
部位ごとの正規化で決めたが、行間の差がどう見えるかは実データ次第。

## 15. 決定済み

| 項目 | 決定 |
| --- | --- |
| 同一種目を1日に複数回 | **1日1エントリ。再編集で後からセットを足す**（§2.1） |
| アーカイブ種目 | **記録画面では隠す／グラフ・表には出す**（§5.1） |
| `MuscleGroup` | **固定6値の enum**（§2） |
| 種目プリセット | **部位ごと4〜5種、計28種**（§3） |
| テスト | **`vitest` を devDependency に追加、`src/lib` の純関数のみ**（§9） |
| `Exercise.id` | `crypto.randomUUID()` |
| 種目の並び替え | **持たない。**一覧を部位ごとの見出しで区切ったので、探し方が「何番目か」から「どの部位か」に変わった（上下ボタンは撤回） |
| 種目一覧の並び | 部位ごとに見出しを付け、主部位で切る。行のタグは補助部位だけ（主部位は見出しが持つ） |
| 同名種目の重複 | 許す（警告のみ）。改名の自由を優先 |
| サニタイズ値域 | 重量 0〜500kg / レップ 1〜100 / `step` 0.25〜25 / `bodyweightFactor` 0〜2 |
| 空状態 | 既存 `HomeView` の `emptyState` と同じ書式 |
| サンプルデータの seed | **デモ向けビルドだけ**に入れる（`vite build --mode demo`）。自分の記録として使う側に他人の数字を入れない。seed 分岐で筋トレを落とさない点は維持（§9） |
| 種目カタログ | localStorage に投入しない。コード内定数（§3） |
| 一括削除 | 「実績データを削除」と「すべて削除」の2系統（§2.2） |
| 種目マスタの初期状態 | **空。**カタログから自分でやる種目だけ選ぶ（§3 / §11-17） |
| 種目の削除 | **記録ごと消す**（件数を出して確認）。残したまま候補から外すのは「非表示」（§2.1 / §11-16） |
