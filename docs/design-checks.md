# トレーニング種目のレビュー 設計メモ

`design-training.md` の続き。組んだトレーニングの構成に対して、
**明らかにおかしい配置を検出するフィルタ**を足すための設計。実装前の合意事項。

元の要求は8つの警告と「メニュー（曜日 × 種目 × セット数）」というデータを持っていたが、
既存仕様と突き合わせた結果、**半分は既にあるか、既に撤回済みだった**。
落としたものと理由は §7 に残してある（蒸し返さないため）。

---

## 1. 背骨

> **最適なメニューを生成しない。組んだ構成を検算するだけ。
> 検査の入力は記録とプリセットで、計画データを新しく持たない。**

`design-training.md` §1.1 は「指示をしない／計画型を採らない」を背骨に置き、
§11-3 で「今日のメニュー表」を、§11-6 で `Routine`（メニュー）を撤回している。
この機能はそこへ戻るものではない。

判定の対象は **人の実績ではなく、いま組んでいる構成という設計物**。
「未達」を突きつける相手が人ではないので、§1.1 の「未達という状態を作らない」とは衝突しない。
ただしアプリが否定的な語彙を持つのはこれが初めてで、その自覚は要る（§6）。

### 1.1 なぜ部位別セット数では足りないか

既存の配分の見方は**部位別ワークセット数**ひとつ（`design-training.md` §4.6 / §5.3）。
これは「どの部位をどれだけやったか」には答えるが、
**複数種目にまたがって消費されるが、どの種目の主目的でもない負荷**は数えられない。

| | 部位別セット数で見える | 見えない |
| --- | --- | --- |
| 胸を何セットやったか | ✔ | |
| 腰椎が1日に何回動員されたか | | ✔ デッド・スクワット・RDL の主部位はバラバラ |

→ **これを「共有資源」として別に追跡する。** 切り分けの基準は
「部位別セット数では見えない負荷だけを資源にする」。

### 1.2 資源は腰椎ひとつ

グリップも同じ性質を持つが、**資源としては追わない**（§7-10）。
0〜10 の数値が効くのは日内合計と残存疲労の判定だけで、そのどちらも観測された失敗ではなかった。
実際に起きた「前腕直接種目の翌日に引き系」は真偽値 2 つで判定できる。
加えてグリップは回復が速く（前腕屈筋群は小さく持久的）、外したときの結果も軽い。

三角筋前部や上腕三頭も候補になるが、こちらは**部位の疲労**（§1.3）が受け持つ。

型は `Record<ResourceId, …>` のままにしてあるので、要ると分かったら足し直せる。

### 1.3 部位の疲労は「資源」とは別の仕組みで持つ

部位ごとの回復も見たいが、**資源と同じやり方は採らない**（種目ごとに 0〜10 を決めることになる）。

部位の消費量は**すでにアプリの中にある**。`buildWeeklySets` が使っている
「主部位は 1 セット、補助部位は種目ごとの係数ぶん」がそれで、
係数は利用者が種目ごとに決めたもの——こちらが発明した値ではない。
ここに資源とまったく同じ線形減衰を当てれば、**種目マスタを 1 行も増やさずに**
部位別の残存疲労が出る。

| | 腰椎（資源） | 部位 |
| --- | --- | --- |
| 消費量の出どころ | 種目ごとの 0〜10（手入力） | 部位別セット数（既存） |
| セット数を掛けるか | **掛けない**（置いたかどうか） | **セット数そのもの** |
| 積み上げるか | **積み上げる**（連日で増える） | **積み上げない**（1 回ぶんが上限） |
| 出しかた | 線形減衰（既定 1日 5）→ 日数に換算 | セット数から**空ける日数**を決める |
| 警告 | 出す（W2 / W4） | **出さない**（§6.1） |

**部位だけ積み上げないのは、消費がセット数に比例するため。**
毎日足し込む式にすると、回復量を上回る週次ボリュームで**際限なく積み上がる**。
背中を週 20 セットやる人は「22 日ぶん残っている」に到達し、
出ているのは疲労ではなく累積ボリュームになる。
腰椎で積み上げが成立するのは、消費がセット数に比例しない（置いたか否かの 0/1 に近い）ため。

**線形減衰そのものも部位には使えない。** 比例で減らすと 16 セットのセッションに
「7 日ぶん」と答える。ボリュームに比例して回復が延びる前提だが、**実際の回復は飽和する。**

→ 部位は **セッションの大きさから空ける日数を決める**（§5.4）。

**部位には警告を出さない。** 6 部位ぶん足すと警告の総数が倍以上になり、
全体が読み飛ばされる側に倒れる。種目を足すときに「この部位はまだ残っている」が
見えていれば、判断するのは本人で足りる（§1.1）。

## 2. 何を検出するか

元仕様の8つのうち、**6と7は作らない。** 既存画面が同じことを既にしている。

| # | 検出するもの | 採否 |
| --- | --- | --- |
| W1 | セッションの所要時間が上限を超過 | 採用（条件つき／§4） |
| W2 | 1日の腰椎負荷の合計が上限超過 | 採用 |
| W3 | 1日のグリップ負荷の合計が上限超過 | **不採用**（§7-10） |
| W4 | 腰椎の残存疲労が閾値超の日に、腰椎の高負荷種目が置かれている | 採用 |
| W5 | グリップの残存疲労が閾値超の日に、グリップの高負荷種目が置かれている | **不採用**（§7-10） |
| W6 | 優先部位の週間セット数が目標未達 | **不採用**（§7-1） |
| W7 | 維持部位の週間セット数がレンジ外 | **不採用**（§7-1） |
| W8 | 前腕直接種目の翌日に引き系種目が置かれている | **不採用**（§7-13） |

番号は元仕様のまま残す。欠番があるほうが、後から「6はどうなった」を追える。

**すべて警告。エラーは設けない。** 保存も入力も止めない。

### 2.1 失敗例と担当

元仕様が挙げた実際の設計失敗が、それぞれどれで捕まるか。

| 起きたこと | 担当 |
| --- | --- |
| 軸荷重種目が週4日に分散し、腰椎の回復窓が消えた | W4 |
| 前腕直接種目が引き系の前日に来て、懸垂・デッドが落ちた | W8 |
| カーフレイズなど回復コストの低い種目にボリュームが偏り、時間だけ消費した | **W1** |
| 胸6 に対し背中3 の非対称に気づけなかった | 既存の目標タブ（実装なし） |

3つ目が W1 の担当になるのが重要。**負荷値はセット数に依存せず（§3.1）、
時間だけがセット数に比例する。** カーフレイズを5セットに増やしても腰椎・グリップは動かず、
時間だけが伸びる。これがそのまま「時間だけを消費している」という事実になる。

## 3. データモデル

`AppData` を version 3 に上げ、`Exercise` に4フィールド、`AppData` に2キー足す。
既存キーは無改変。

### 3.1 種目に足すもの

```ts
export type ResourceId = 'lowBack' | 'grip';

export interface Exercise {
  /* ...既存 9 フィールドは無改変... */

  /**
   * 共有資源の消費。0 は「この資源を使わない」。
   * **セット数を掛けない。** その日に種目を置いたかどうかで決まる。
   */
  loads: Record<ResourceId, number>;
  /** 前腕を直接鍛える種目か（W8） */
  forearmDirect: boolean;
  /**
   * 1 セットあたりの所要時間（分）。**null なら `checks.minutesPerSet` を使う。**
   * 休憩が明らかに長い種目だけ上書きする（§4）。
   */
  minutesPerSet: number | null;
}
```

**基本時間（ラック確保・プレート付替）は持たない。** その固定コストは
「その種目の 1 セットは長い」に畳める。デッドリフト 4.5 分／カーフレイズ 3 分の差が
そのまま準備コストの差になっている。パラメータが 2 つから 1 つに減り、
種目ごとに「基本何分・1 セット何分」を分けて考える必要がなくなる。
→ 代償はセット数の少ない日で短めに出ること（§4.4）。

**「引き系種目か」のフラグは持たない。** `loads.grip` が高い種目がそのまま引き系になる
（デッドリフト・懸垂・ロウはすべてグリップ負荷の上位）。
フラグを別に持つと、グリップ負荷 9 なのに引き系フラグが false、という矛盾状態を作れてしまう。
W8 は「前日に `forearmDirect`、当日に `loads.grip >= heavy`」で判定する。

**器具種別（ラック/マシン/ケーブル/ダンベル/自重）は持たない。**
`Equipment` と `catalogEquipment()` が既にあり（`exerciseCatalog.ts`）、
5値の別軸を足すと器具が2つ並ぶ。`design-training.md` §11-23 が
`loadType` + `perSide` を1つに統合した理由と同じ。
時間の既定値をここから引く用途もない（§4 で既定値を持たないと決めたため）。

**レストポーズ可否は持たない。** どの警告にも効かない。
§11-25 が `loadMode: 'none'` を「定義から自動的に従うならフラグは要らない」で消したのと同じ。

**「伸ばす対象フラグ」は持たない。** `Exercise.goal.type` が既にこれ。
`'maintain'` が「これ以上は伸ばさないと決めた種目」で、§15 に決定済みとして載っている。
別に持つと、目標が `weight` なのにフラグが false という矛盾を作れる。

### 3.2 閾値

```ts
export interface ResourceRule {
  /** 1 日の合計の上限。日内集約の防止 */
  dailyMax: number;
  /** 1 日あたりの回復量（線形減衰） */
  recovery: number;
  /** この残存を超えている日に高負荷種目を置いたら警告 */
  residualMax: number;
  /** 「高負荷」とみなす種目単体の負荷値 */
  heavy: number;
}

export interface CheckSettings {
  /** 1 セッションの上限（分）。null なら W1 を出さない */
  sessionMinutes: number | null;
  /** 1 セットあたりの時間（分）の既定値。種目が null のときここに落ちる（§4） */
  minutesPerSet: number;
  /** 資源ごとに同じ形。3 つ目を足すときにデータの形を変えずに済む（§1.2） */
  resources: Record<ResourceId, ResourceRule>;
}
```

`sessionMinutes` の既定は **90**、`minutesPerSet` の既定は **3**。
資源の既定値は下のとおり。

| | lowBack | grip |
| --- | --- | --- |
| `dailyMax` | 18 | 18 |
| `recovery` | 5 | 5 |
| `residualMax` | 5 | 5 |
| `heavy` | 7 | 8 |

### 3.3 許容済み

```ts
export interface AppData {
  /* ... */
  checks: CheckSettings;
  /** 許容済みにした警告のキー（`ルール|スコープ`） */
  suppressed: string[];
}
```

**サプレスは必須機能。** 意図して受け入れた警告（ショルダープレスの腰椎負荷を承知で置く等）が
毎週出続けると、警告そのものが読み飛ばされる。

| 警告 | スコープ | キーの形 |
| --- | --- | --- |
| W1 | 日 | `time\|d:2026-08-30` |
| W2 / W3 | 日、またはプリセット | `lowBack.daily\|d:...` / `grip.daily\|p:<presetId>` |
| W4 | 種目 | `residual\|lowBack\|e:<exerciseId>` |
| W8 | 種目（前腕直接の側） | `forearm\|\|e:<exerciseId>` |

日スコープは「今日は承知」、種目スコープは「この種目については以後ずっと承知」。
**解除できること。** 一方通行にすると、押し間違いが永久に残る。
設定 > トレーニング > 構成チェック に一覧を置く（§5.3）。

### 3.4 移行

`design-training.md` §9 の作法に従う。

- `sanitizeData()` で足りないキーを既定値で補う。v2 のバックアップはそのまま読める
- **移行の判定は版で行う。キーの有無では行わない。**
  キーの有無は「途中のビルドが既定値を書き戻した」と「本人がその値を選んだ」を区別できない。
  v3 では実際に 2 度それが起きた（`loads: 0` と `axial: false`）。
  どちらも保存されたあとは「本人の選択」として尊重され、二度と戻らなくなった。
  版で見れば、その世代のデータをまとめて読み直せる（`CHECK_FIELDS_VERSION`）
- **種目のレビュー値は、版が古ければ値があってもカタログから引き直す。**
  保存済みの種目はこれを持たないので、0 のまま読むと
  「カタログからデッドリフトを入れてあるのに腰椎 0」となり、既存ユーザーだけ判定が効かない。
  3 つのどれも持っていない種目は v2 以前のデータなので、**ID からカタログを引き直して埋める**
  （`catalogCheckValues`）。1 つでも持っていれば v3 以降の保存なので、
  **0 も選択として尊重する**（「この種目の腰椎は数えない」と決めた結果を移行が上書きしない）
- `DATA_KEY` は `bodymake.data.v1` のまま変えない
- **保存ガードは入れない。** v4 をデプロイしたあと古い版に戻すと `checks` / `suppressed` と
  種目の構成チェック値が落ちる。これは許容する。
  設定 &gt; 一般 &gt; データの「ときどき JSON を書き出しておくと安全です」がそのまま復旧経路で、
  版が上がったことを知らせる文言は足さない（読む側にできることが増えないため）

## 4. 時間の扱い

W1 だけ他と性格が違うので分けて書く。

```
T = Σ 種目ごと ( セット数 × (種目の minutesPerSet ?? checks.minutesPerSet) )
```

### 4.1 なぜ持てるか

`design-training.md` は時間について2度判断している。

- §11-2 — **アプリがセットの時刻を自動記録すること**を撤回。
  後日入力で入力時刻を記録してしまい、しかも *それらしい値* が残るので壊れていても気づけない
- §12 — **休憩タイマー・インターバル指示**を不採用。「時間軸に依存しない設計にした」

どちらも「アプリが測る」「アプリが指示する」の話。
**組んだ構成の長さを見積もって、利用者が決めた上限と比べる**ことは対象外。
測りもしないし、何分でやれとも言わない。

### 4.2 なぜ「回数 × 時間」を採らないか

セットの所要時間は**休憩が支配**する。挙上そのものは数十秒しかない。

| | 挙上 | 休憩 | 1 セット計 | 1 レップあたり |
| --- | --- | --- | --- | --- |
| デッドリフト 5 レップ | 約15秒 | 約180秒 | **3.3分** | 39秒 |
| サイドレイズ 15 レップ | 約30秒 | 約60秒 | **1.5分** | 6秒 |

種目間のばらつきは、1 セットあたりなら 2.2 倍、1 レップあたりだと 6.5 倍。
**回数で掛けるほうが値が敏感になり、外したときの誤差が大きい。**

同一種目内はもっと悪い。デッドリフト 5×3 と 5×10 は
休憩が同じなので所要時間もほぼ同じだが、回数で掛けると 3.3 倍違うと出る。
高重量・低レップほど短く見積もられるので、
**いちばん長引くセッション（軸荷重種目が集まった日）をいちばん過小評価する。**

加えて W1 は打つ前に検算するためのものなので、回数モデルでは入力前が常に 0 分になる。

→ **セット数で掛ける。**

### 4.3 既定値は 1 つだけ持つ

種目ごとに分数を発明して 75 種に配ると、根拠のない値が根拠ありげに並び、
外れていても検出できない（§11-2 と同型）。
かといって全部を利用者の実測待ちにすると、埋め終わるまで W1 が沈黙し、機能が死ぬ。

→ **グローバル既定を 1 つ持ち、種目ごとに上書きできる形にする。**

| | |
| --- | --- |
| `checks.minutesPerSet` | 全種目のフォールバック（既定 3 分） |
| `Exercise.minutesPerSet` | 種目ごとの上書き。**null が既定** |

カタログに上書きを入れるのは、**休憩が明らかに長い高重量コンパウンドだけ**。

| 種目 | 1 セット |
| --- | --- |
| デッドリフト / スクワット / ベンチプレス / ショルダープレス / RDL | 4.5 分 |
| 上記以外 | （null → 既定 3 分） |

腰椎・グリップ負荷について「順序が明確な種目だけ値を置き、他は 0」と決めたのと同じ原則。
根拠は 1 文で書ける——**高重量コンパウンドは休憩が長い。**

この形の利点は、ずれたときの直し方が 1 か所で済むこと。
数週間使って見積もりが systematically ずれていたら、既定の 3 分を動かせば全体が直る。
種目ごとに配ってしまうと、75 個ずれた状態からどこを直すか決められない。

### 4.4 精度は求めない

W1 が判定したいのは「90 分の枠に 120 分ぶん詰めていないか」で、2 倍スケールの問い。
「88 分か 92 分か」は当てなくていいし、当てられない。

見積もりは ±20% 程度ずれる。とくに**セット数の少ない日は短めに出る**
（準備コストを 1 セットあたりに畳んだ副作用／§3.1）。
→ 上限は実際の枠より少し短めに置くのが正しい使い方。
分単位の管理には使わない。

パラメータを増やせば精度は上がるが、2 倍スケールの判定は変わらない。
回数の項を足しても寄与は全体の 1 割弱で、増やしたぶんだけ
「なぜこの分数になったか」の説明が長くなる（§12）。

### 4.5 内訳は出さない

表示は種目ごとの合計値と、その日の合計だけ。
「基本◯分＋1 セット◯分」という内訳は持たない（そもそも分けて持っていない）。

### 4.6 プリセット画面では時間を出さない

プリセットは種目しか持たない（`types.ts` の `Preset`／§15「重量もレップもセット数も持たない」）。
セット数を掛ける相手がないので、**プリセット画面に時間は出さない。**

プリセットにセット数を持たせる案は採らない。先に値を決めると計画型になる（§1.1）。

## 5. 計算の定義

### 5.1 消費量の出どころ

| 対象 | 何を読むか | 理由 |
| --- | --- | --- |
| 編集中の日 | `workouts[date]` の生エントリ | いま並べている**設計**。値を打つ前でも検算したい |
| それより前の日 | `sessions`（`buildSessions` 後） | **やった事実**。値が1つも入っていない日は消費していない |
| プリセット | `preset.exerciseIds` | 日付を持たない。W2 / W3 だけ成立する |

編集中の日だけ生エントリを読むのが要点。`hasAnySet` で落とすと、
種目を並べた直後（まだ何も打っていない）に警告が出ず、検算の意味がなくなる。
逆に過去の日で生エントリを読むと、種目を並べて閉じただけの日が消費として数えられる。

### 5.2 日ごとの消費

```
consumed(資源, 日) = その日に置かれた種目の loads[資源] の合計
```

**セット数を掛けない。** デッドリフトを3セットやっても5セットやっても腰椎10。
負荷値は順序でしかなく（§3.1）、セット数を掛けるとその順序が
「セット数 × 主観値」という別の量に化ける。
ボリューム偏重は W1（時間）が担当する（§2.1）。

### 5.3 残存疲労（線形減衰）

資源と部位で**式が違う**。消費の性質が違うため（§1.3）。


**1日あたり固定量ずつ減る。「N日で回復」という固定日数方式は採らない。**
消費量が大きい日ほど後を引く挙動が要る。

```
after(d)  = max(0, after(d-1) − recovery) + consumed(d)
before(d) = max(0, after(d-1) − recovery)      ← 判定に使う「その日の朝の残り」
```

`recovery = 5` なら、デッドリフト10 の翌日は 5 残り、スクワット8 の翌日は 3 しか残らない。
固定日数方式ではこの差が出ない。

遡る範囲は **対象日の30日前まで**。`recovery = 5` で30日ぶん引くと 150 になり、
1日の消費がそれを超えることはない（種目あたり最大10）。

### 5.3.1 画面には「何日ぶん」で出す

素の値（腰椎 7）は**順序をつけるための目盛りで、読む足場が画面に無い。**
線形減衰なので割り算 1 つで日数になる。

```
何日ぶん = ceil( 残り ÷ 回復量 )
```

新しい仮定は入っていない。**表示上の変換であって、判定には使わない**
（日数に丸めると残り 3 と 5 がどちらも「1 日ぶん」になり、閾値の意味が変わる）。

### 5.4 部位の空き（今日その部位をやってよいか）

答えたい問いが資源とは違う。「どれだけ疲労が溜まっているか」ではなく
**「今日この部位をやってよいか、過剰でないか」**。

```
空ける日数 = 5セットまで 1日 ／ 6〜10セット 2日 ／ 11セット以上 3日
あと何日   = max( 空ける日数 − 経過日数 )     ← 直近のセッションぶんで最大のもの
```

**上限の 3 日は恣意的な数字ではない。** 回復の窓は 24〜72 時間で、
それを超えて空けても回復は進まない（超えた分は detraining 側に働く）。
線形減衰で 16 セットに「7 日ぶん」と答えていたのは、ボリュームに比例して延びる前提のため。

段は 3 つだけ。細かく刻んでも、決められるのは「今日やるか、1〜2 日待つか」しかない。

最大を採るので、大きい古いセッションと小さい直近のセッションの両方が拾える
（3 日前に 12 セット、昨日 2 セットなら、効いているのは前者）。
構造上 3 日を超えないので、現実離れした日数は出ない。

**設定を持たない。** セット数から日数を決めるだけで、調整する係数がない。
個人差の補正は初期版に入れない（§7-7）。

**根拠のセッションを必ず添える**（「胸 あと1日（昨日 6セット）」）。
なぜその日数なのかを追えない数字は、読み飛ばされるか誤って信じられるかのどちらかになる。

### 5.4 各警告の判定

| # | 条件 |
| --- | --- |
| W1 | `sessionMinutes != null` かつ Σ(セット数 × (種目の `minutesPerSet` ?? 既定)) > `sessionMinutes` |
| W2 | `consumed(lowBack, d) > resources.lowBack.dailyMax` |

| W4 | `before(lowBack, d) > residualMax` かつ その日に `loads.lowBack >= heavy` の種目がある |

| W8 | 前日に `forearmDirect` の種目があり、その日に `pulling` の種目がある |

W1 のセット数は打った行数（空行も含む。並べた時点で設計に入っているため）。

### 5.5 理由を必ず添える

**利用者が警告の理由を追えなくなったら、その警告は機能していない。**
各警告は本文と別に「何を見てそう出たか」を持つ。

```
腰椎の疲労が残っている日にデッドリフトが入っています
  腰椎の残り 7（3/8 デッドリフト 10 → 5 回復 → 5、3/9 スクワット 8 → …）
```

`design-training.md` §12 の「ルールが1段落で書けないものは説明責任を果たせない」に従う。
線形減衰は1段落で書ける。書けなくなったら、その拡張は入れない。

## 6. 画面

置く場所は **組み合わせを組んでいるその場** ——記録画面とプリセット画面。
週を俯瞰する新しい画面は作らない（作れば §11-3 の「メニュー表」に戻る）。

### 6.1 記録画面（トレーニング）

**画面に出す名前は「レビュー」。**「構成チェック」は何の構成を何に照らすのかが読めず、
「気になる点」も出しているものの名前になっていなかった。
出しているのは指摘そのものなので、そう名乗る（この文書では機能名として構成チェックも使う）。

並びは **プリセット → レビュー → 回復 → 種目カード**。
レビューは「いま組んだものへの指摘」なので種目カードのすぐ上が素直で、
回復は入口 1 行だけなので下に置いても埋もれない。

プリセットカードのすぐ下、種目カードより上。**種目が1つ以上ある日だけ出す。**

**警告が 0 件ならカードごと出さない。** 「レビュー なし」と書かれた枠が毎日そこにあると、
中身が入った日にも枠として読み飛ばされる。出るときだけ出るから目に入る。

**見積もり時間は常に出す。** 上限を超えたかどうかは W1 が言うが、
枠に対してどれくらい積んだかは、越える前から見えていないと組み替えようがない。
カードにはせず、カードのあいだに置く 1 行にする（枠を作ると種目カードがそのぶん下へ流れる）。

```
回復                          背中・肩・腕・体幹 が回復済み（腰椎は あと1日）  ›

レビュー                                            2件

  ⚠ 腰椎の疲労が残っている日にデッドリフトが入っています
     2日ぶん残っています（3/8 デッドリフト → 3/9 スクワット）  [ 許容する ]
  ⚠ 1日の腰椎負荷が上限を超えています
     25 / 上限 18 — デッドリフト10 + スクワット8 + RDL7        [ 許容する ]

  見積もり時間 42分 / 上限 90分
```

- **回復は別のカードに分ける。** 見る場面が違う（回復は種目を選ぶ前、構成チェックは選んだあと）。
  同じカードに積むと、種目を 1 つ足すたびに両方が動いて、どちらを読んでいるのか分からなくなる
- **回復はカードを入口だけにして、中身はダイアログで出す。**
  7 行を常時置くと種目カードが毎回それだけ下へ流れる。見るのは献立を決める一瞬だけ
- **回復は種目が 1 つも無い日でも出す。** 空きを見てから種目を選ぶのが本来の順序で、
  何も置いていないときこそ必要になる（構成チェックはその逆で、置いてから出る）

### 6.1.1 回復ダイアログ

```
回復

筋肉の疲労
  胸    ▓▓▓▓▓░░░░░  あと1日
        昨日 6セット
  背中  ▓▓▓▓▓▓▓▓▓▓  回復済み
        4日前 9セット
  …
  5セットまで翌日 / 6〜10セット 中1日 / 11セット以上 中2日。
  筋肉の疲労は積み上がらず1回ぶんで頭打ちになるので、直近のセッションだけで決めます。

腰椎の疲労
  腰椎  ▓▓▓▓▓░░░░░  あと1日
        デッドリフト・スクワット
  腰椎の疲労は日をまたいで積み上がるので、合計を追って1日ずつ引いた残りで出します。
```

- **筋肉と腰椎はセクションを分ける。** 疲労の溜まり方が違うのに 7 行を 1 つの表に並べると、
  同じ物差しの同じ量に見える。腰椎は部位ではないし、積み上がりかたも違う
- **状態の言葉は「回復済み／あと N 日」。**「今日やれる」とは書かない。
  それは許可を出す言い方で、決めるのは本人（§1.1）。
  アプリが言えるのは体がどうなっているかまでで、やるかどうかはその先にある
- **カードの要約に出すのは回復している側。** 「脚・胸 は空くのを待っています」だと、
  できないことの一覧を毎回読むことになる。献立を決める場面で要るのは「どこが使えるか」
- **進み具合はゲージで出す。ただし目盛りは「あと何日」だけから引く。**
  「経過日数 ÷ そのセッションに要る日数」にすると分母がセッションの大きさで動き、
  胸（8セット・2日必要・1日経過＝50%）と脚（16セット・3日必要・2日経過＝67%）が
  どちらも「あと1日」なのにバーの長さが違う。**バーが数字と別のことを言うと、まばらに見える。**
  目盛りは全行で共通にする（行ごとに分母が違うと、同じ「あと1日」がまた別の長さになる）
- **根拠は必ず添える**（昨日 6セット／デッドリフト・スクワット）。
  追えない数字は読み飛ばされるか、誤って信じられる

- **数字は警告が無くても常時出す。** 警告は境界を越えた瞬間だけ出るので、
  それだけだと「あと少しで越える」が見えない。日付ナビで日を移せば推移も追える
- **出すのは警告と見積もり時間だけ。** 腰椎の日内合計はゲージで常時出していたが、
  上限を超えたかどうかは W2 が警告として言う。越えていない日にゲージだけ置いても、
  毎回そこにあるものは読まれなくなる。判定はこれまでどおり行っていて、
  見えなくなったのは「あと少しで越える」の一段だけ
- **目盛りの数字（25 / 18）は画面に出さない。** 25 は順序をつけるために作った値で、
  多いのかどうかを読む足場が無い。素の値は調整するときにだけ要るので、
  設定画面と警告の詳細に残す
- **残っていない部位も名前を出す。** 行ごと消すと、無いのか見えないのかが分からない
- 行の形（名前・バー・値）は目標タブの部位の行にそろえる。同じ読み方で読める
- 警告は入力中に出たり消えたりする。`design-training.md` §7.2 が
  「予定行を並べず、やったことが積み上がる形」と決めているので、
  記録画面には「組み合わせが確定した瞬間」が存在しない。
  プリセットを呼び出した直後だけが全体の揃う点で、そこが自然な検査点になる

### 6.2 プリセット画面（設定 > トレーニング > プリセット）

  「警告が出ない＝問題がない」と読まれる。穴を数字で出す

## 7. 落としたものと理由

**1. W6 / W7（部位別の週間セット数）**
`TrainingGoalBoard` が6部位すべてについて「今週のセット数 ÷ 目標」＋メーター＋到達率を既に出し、
`GroupSetsHeatmap`（ホーム）が週×部位の配分推移を持っている。完全な重複。
→ 不採用。胸6 / 背中3 の非対称は既存画面で見える。

**2. 「優先部位 / 維持部位」の区別と 10〜16 レンジ**
既存の「その部位の目標を決めたか / 決めないか」がそのまま同じ区別で、
`TrainingGoalBoard` の目安プリセットが `少なめ 8 / 標準 12 / 多め 16 / 決めない` を既に持つ。
→ 新設しない。

**3. メニュー（曜日 × 種目 × セット数）**
§11-3「今日のメニュー表（計画型の画面）」と §11-6「`Routine`（メニュー）」で撤回済み。
曜日を固定して管理したいわけでもない（「いつ、どの種目をやったか」を基準にしたい）。
→ 計画データを持たず、記録とプリセットを検査対象にする（§5.1）。

**4. 器具種別（5値）／レストポーズ可否／伸ばす対象フラグ**
順に、既存 `Equipment` との二重／どの警告にも効かない／既存 `goal.type` との二重。
→ いずれも持たない（§3.1）。

**5. 「引き系種目」フラグ**
`loads.grip` から導出できる。フラグを別に持つと矛盾状態が作れる。
→ 持たない（§3.1）。

**6. 時間を「回数 × 1 レップの時間」で出すこと**
休憩が支配するので、回数はセット数より悪い予測子になる。
同一種目でも 5×3 と 5×10 で見積もりが 3.3 倍違い、
実際にいちばん長引く高重量・低レップの日をいちばん短く見積もる。
打つ前は 0 分になるので、組む段階の検算にも使えない。
→ セット数で掛ける（§4.2）。

**6b. 種目ごとに所要時間を配ること／利用者の実測待ちにすること**
75 種に分数を配れば根拠のない値が根拠ありげに並び、
実測待ちにすれば埋め終わるまで W1 が沈黙して機能が死ぬ。
→ **グローバル既定 1 つ + 高重量コンパウンド 5 種の上書き**（§4.3）。

**6c. 基本時間（ラック確保・プレート付替）を別に持つこと**
「その種目の 1 セットは長い」に畳める。
パラメータが 2 つから 1 つに減り、判定は変わらない（§4.4）。
→ 持たない。代償はセット数の少ない日で短めに出ること。

**13. グリップ（前腕直接 → 引き系の並び）**
仕様書が挙げた失敗のひとつだったが、利用者の判断で廃止。
残っていたのは真偽値 2 つ（`forearmDirect` / `pulling`）だけで、
判定も「前日に前腕直接、当日に引き系」の 1 本。
→ 種目のフラグは `axial` ひとつになり、指摘は 2 つ（時間・軸荷重の連日）に。

**14. 指摘に「改善するなら」を添えること（採用）**
`design-training.md` §1.1 は「指示をしない」と決めているが、
**書くのは「その判定が偽になる条件」だけ**に限れば、指示ではなく判定の言い換えになる。
「重量を上げましょう」は指示、「セットを 3 つ減らすと上限に収まる」は判定の裏返し。
指摘を出しておいて消し方を書かないのは、読む側に判定の再現を強いる。
条件形（〜なら）にしてあるのは、やるかどうかを決めるのが本人だから。

**12. 腰椎を「疲労の量」として追うこと（0〜10 の負荷値・線形減衰・残存）**
1 本の数字に、時定数の違う 4 つの層を代表させていた。

| 層 | 時定数 |
| --- | --- |
| 脊柱起立筋 | 24〜72h |
| 神経系・全身性 | 48〜96h |
| 椎間板・靭帯 | 数日〜週（無血管性で拡散依存） |
| 椎弓・終板 | 週〜月（もはや「抜ける」対象ではない） |

当たっていたのは上 2 層だけで、下 2 層は表せていなかった。しかも
**「あと何日」という枠組みは、いちばん戻らないものに「待てば戻る」を含意する。**
椎間板の内部はほぼ無神経で症状も早期には出ないので、
「回復済み」と出すのは二重に誤っている。

天井（1 日の上限）を付けて「あと 9 日」を抑えたのも、
**積み上がりという唯一の信号を潰す方向**だった。表示の不合理は消えたが、意味は劣化した。

→ **疲労のモデルをやめ、`軸荷重種目か` の真偽値と、置いた日付だけにする。**
   「いつ置いたか」は記録そのもので、推定も減衰も定数も要らない。
   当初の失敗例（軸荷重が週 4 日に分散）はこれで捕まる。
   同時に「RDL は 8 か 0 か」「18 か 20 か」「高負荷とみなす値とは」という
   0〜10 の目盛りに由来する問いが、すべて消えた。

**10. グリップを資源として追うこと（0〜10 の数値）**
仕様書はグリップを腰椎と対等の資源として置いていたが、**数値が効く先が無かった。**
W8（前腕→引き系）は真偽値 2 つで判定でき、数値を使うのは W3（日内合計）と W5（残存疲労）だけ。
そのどちらも仕様書の失敗例に対応するものが無い。
加えて前腕屈筋群は小さく持久的で回復が速く、腰椎と同じ「1日5ずつ」を当てる根拠もない。
外したときの結果も違う（腰椎は故障、グリップは懸垂が1レップ落ちる）。
→ **W3 / W5 を落とし、W8 だけ `forearmDirect` + `pulling` の真偽値で残す。**
   15 種目ぶんの数値を決める必要がなくなり、「RDL のグリップは 8 か 0 か」という
   答えの出ない問いも消えた。

**11. 「順序が明確な種目だけ値を置く」という決め方**
腰椎負荷を仕様書が名前を挙げた 5 種目だけに入れた結果、
ベントオーバーロウ（前傾保持）とレッグプレス（背中が支えられる）が同じ 0 になった。
**0 は中立ではなく「この資源を使わない」という主張**なので、これは値を入れていないのではなく
間違った値を入れている。順序関係——数値の唯一の根拠——を自分で壊していた。
→ 基準を **「その資源を使うかどうか」** に変え、使う種目には必ず 0 より上を置く（§7-11 は §3.1）。

**7. キャリブレーション（個人差の補正係数）**
回復能力は個人差があり減量期と維持期でも変わるが、
何を補正しているか分からないまま係数が動く状態を避ける。
数週間運用してズレを実感してから。
→ 初期版に入れない。

**8. 感度分析（係数を振って判定の安定性を見る機構）**
→ 初期版に入れない。

**9. 部位の疲労を「資源」として持つこと（種目ごとに 0〜10 を決める）**
「ベンチの三角筋前部への貢献は胸の何割か」に堅い答えが無いので見送っていたが、
**答えは既にアプリの中にあった。**`subGroups` の係数がそれで、利用者が種目ごとに決めてある。
→ 資源としてではなく、**部位別セット数に同じ線形減衰を当てる**形で採用（§1.3）。
   種目マスタは 1 行も増えない。ただし警告は出さない。

## 8. 採らないもの（恒久）

| 採らない | 理由 |
| --- | --- |
| 最適なメニューの生成・提案 | §1.1。フィルタであって最適化エンジンではない |
| 総挙上量を判定材料にすること | §11-18 / §11-26。種目をまたいだトン数の合算は意味を持たない |
| 種目をまたいだ総セット数を時間の代理にすること | 同上。デッド3セットとカーフレイズ3セットは時間コストが違う |
| エラー（保存や入力を止める） | すべて警告。判断するのは本人 |
| アプリが所要時間を計測すること | §11-2 |
| 警告の自動的な優先順位づけ・スコア化 | ルールが1段落で書けなくなる（§12） |

## 9. 決定済み

| 項目 | 決定 |
| --- | --- |
| 検査の入力 | **記録（`workouts`）とプリセット。**計画データを新設しない |
| 警告を出す場所 | **記録画面とプリセット画面。**組み合わせを組んでいるその場 |
| 警告の数 | **4つ**（W1 / W2 / W4 / W8）。W6・W7 は既存画面と重複、W3・W5 はグリップを資源から外したため不採用 |
| 追跡する資源 | **腰椎ひとつ。**型は Record のままにして、足し直せるようにする |
| 負荷値の性質 | 測定値ではなく順序。絶対値の精度は求めず、閾値を保守的に置く |
| 負荷値とセット数 | **掛けない。**置いたかどうかで決まる。ボリューム偏重は W1 が担当 |
| 回復 | **線形減衰（1日あたり固定量）。**固定日数方式は採らない |
| 遡る範囲 | 対象日の30日前まで |
| カタログの負荷値 | **その資源を使う種目には必ず 0 より上を置く。**デッド10 / スクワット8 / RDL・フロントスクワット7 / ベントオーバーロウ6 / Tバーロウ・バックエクステンション5 / ショルダープレス4 / アブローラー・ヒップスラスト・シュラッグ3 |
| 0 の意味 | **「使わない」という主張。**「まだ決めていない」ではない。背中が支えられる種目（レッグプレス等）の 0 は正しい 0 |
| 時間の式 | **セット数 × 1セットの時間。**回数は掛けない（休憩が支配するため） |
| 時間のパラメータ | **1 つだけ。**グローバル既定 3 分 + 種目ごとの上書き。基本時間は持たない |
| カタログの所要時間 | **高重量コンパウンド 5 種だけ 4.5 分。**他は null（既定に落ちる） |
| 時間の精度 | **求めない。**±20% ずれる前提で、上限を少し短めに置く |
| 時間の内訳 | 出さない。種目ごとの合計値のみ |
| プリセット画面の時間 | **出さない。**セット数を持たないので部分の部分にしかならない |
| プリセットにセット数 | **持たせない**（§1.1 / §15） |
| 種目に足すフィールド | **4つ**（`loads` / `forearmDirect` / `pulling` / `minutesPerSet`）。うち 2 つは真偽値 |
| 種目の値の置き場所 | **カタログの 75 行に散らさず、`exerciseCatalog.ts` の CHECK 表でまとめて持つ。**どの種目に何を配ったかが一望できないと、根拠のない値が紛れても気づけない |
| 引き系の判定 | **真偽値で持つ。**大小を決める必要がない（引き系かどうかは事実） |
| レビューに出すもの | **警告だけ。**負担のゲージも内訳も置かない |
| 警告 0 件のとき | **カードごと出さない。**枠だけが毎日あると読み飛ばされる |
| 見積もり時間 | **常に出す。**カードにせず、カードのあいだの 1 行にする |
| 部位の空き | **セット数から空ける日数を決める。**種目マスタを増やさず、設定も持たない |
| 回復の置き場所 | **構成チェックとは別カード。**入口だけ置き、中身はダイアログ（§6.1.1） |
| 筋肉と腰椎 | **セクションを分ける。**疲労の溜まり方が違うものを 1 つの表に並べない |
| 状態の言葉 | **「回復済み／あと N 日」。**「今日やれる」は許可を出す言い方になる |
| ゲージの目盛り | **「あと何日」だけから引き、全行で共通。**セッションの大きさを混ぜると、同じ日数でも長さが変わる |
| 部位は積み上げない | **1 セッションぶんが上限。**毎日足し込むと週次ボリューム次第で発散する |
| 部位の上限日数 | **3日。**回復の窓は24〜72時間で、それ以上空けても回復は進まない |
| 画面に出す単位 | **「何日ぶん」。**目盛りの素の値は設定画面と警告の詳細にだけ残す |
| 部位の警告 | **出さない。**6部位ぶん増やすと総数が倍以上になり、全体が読み飛ばされる |
| 残存疲労の推移グラフ | **作らない。**記録画面に「その日の残り」を1行出し、理由は警告に添える |
| サプレス | 必須。日 / 種目 / プリセットの3スコープ。**解除できること** |
| 閾値の置き場所 | 設定 > トレーニング > 構成チェック（3つ目のページ） |
| 負荷値が 0 の種目 | **件数を出す。**穴が見えないと「警告なし＝問題なし」と読まれる |
| データ版 | `version: 4`。保存ガードは入れない（§9 の作法）。ロールバック注意の文言を置く |
| テスト | `src/lib/check.ts` の純関数のみ。§5 の定義表がそのままテストケースになる |
