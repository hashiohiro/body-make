# 保存と再計算 設計メモ

記録が増えたときに入力が重くならないようにするための設計。実装前の合意事項。

きっかけは「IndexedDB へ移したのに入力の重さは解消したのか」という問い。
測ったところ**重かったのは保存ではなく導出**で、移行はそこに効いていなかった。
測定の内容は §2 に、そこから決めた方針を §4 に、検討して**採らないと決めたもの**は §6 に残す
（蒸し返さないため）。

---

## 1. 背骨

> **保存するのは生データだけ。導出値は保存しない。
> 区切るのは書き込みと再計算のためであって、読み込みのためではない。**

`design-training.md` §6.2 の「更新判定も保存せず毎回再計算する」と、
§8-③ の「遡って入れると指標が連鎖して変わる。これは正しい挙動」は維持する。
本メモはその決定を**守ったまま**速くするための設計で、覆すものではない。

---

## 2. 何が重いのか（2026-09-05 実測）

`npm run bench`（`src/lib/perf.bench.ts`）の mean。週3回・1回5種目×4セットの生成データ。

| 測るもの | 1年 | 5年 | 10年 |
| --- | --- | --- | --- |
| **体重入力**（体組成 + トレの両方が走る） | 4.8 ms | 23.7 ms | 65.3 ms |
| トレ入力（トレ側のみ） | 2.2 ms | 16.1 ms | 48.7 ms |
| 体組成のみ（依存を切れたときの目標値） | 1.8 ms | 8.6 ms | 17.1 ms |
| 保存: `structuredClone` | 3.0 ms | 16.6 ms | 35.4 ms |

読み取れること。

- **導出が保存より重い。**IndexedDB 移行は容量の天井を外したが、入力の重さには効いていない。
  むしろ `structuredClone` は `JSON.stringify` より遅く、書き込みのメインスレッド占有は増えた
  （まとめ書きで回数が減ったぶんと相殺）
- **値を 1 つ打つと全期間を作り直している。**`AppData` の同一性が変わると
  `useBodyData` の memo がまとめて外れる
- **体重を打つとトレ側まで走る。**`buildSessions` が自重換算のために `daily` に依存しているため。
  ここを切るだけで 10 年ぶんが 65.3 → 17.1 ms になる
- **読み込みは問題ではない。**起動時の 1 回だけで、10 年ぶんでも 100 ms 程度

数字はこの機械での相対値。実機のスマホは数倍遅い。**絶対値の予測ではなく、
変更の前後で比べるためのもの**として使う。

### 2.1 すでに入れたもの（2026-09-05）

全期間の作り直しのうち、**明らかな重複だけ**を先に除いた（113 ms → 65 ms / 10 年ぶん）。

| 直した場所 | 何をしていたか |
| --- | --- |
| `buildBodyWeightLookup` | 返すクロージャが呼ばれるたびに全期間を線形走査。二分探索にした |
| `computeTrainingStats` | 種目ループの中で `exerciseHistory` を呼び、毎回セッション全体を走査。1 回の走査で索引を作る形にした |
| `buildDaily` | 移動平均で日ごとに配列を 3 つ生成。その場で足す形にした（**足す順序は変えていない**） |

**計算結果は変えていないので、テストは 1 件も書き換えていない。**これが変えていないことの証拠になる。

## 3. 読み込みの局所化は採らない

「古い週は読まずに済ませたい」は自然な発想だが、このアプリでは成り立たない。

ホームと目標画面は**全期間の数字**を出す — 開始値（最初の 7 日の平均）、最長連続記録、
通算セッション数、全部位を一巡した週数、記録日数、種目の種類数。
これらを出す以上、全期間のデータが要る。

古い週を読まずに済ませるには、その週の結果をどこかに持っておくしかない。
**それは導出値の保存**であり、§1 の背骨に反する（詳細は §6）。

そして読み込みは起動時の 1 回だけで、ボトルネックではない。
**局所化したいのは読み込みではなく、打鍵ごとに走る再計算のほう。**

---

## 4. 週で区切る

```
保存するもの   生データだけ。週（日曜〜土曜）ごとのレコードに分ける
              種目マスタ・プリセット・設定・許容済みは週に属さないので別レコード

導出          すべてメモリ上。週単位で memo する。保存しない
```

得られるもの。

| | いま | 週で区切った場合 |
| --- | --- | --- |
| 書き込み | 1.3 MB を毎回（35 ms） | 変わった週の約 3 KB（ほぼ 0） |
| 打鍵ごとの導出 | 全期間（65 ms） | 変わった週だけ（1〜2 ms） |
| 起動時の読み込み | 全部 | **全部（変わらない）** |
| 起動時の導出 | 全期間 | **全期間（変わらない。1 回だけ）** |
| 導出値の保存 | なし | **なし** |

週は既存の集計単位（`design-training.md` の週 = 日曜〜土曜）をそのまま使う。
あとから持ち込む人工的な境界にしない。

### 4.1 境界の注意

- **7 日移動平均は週を跨ぐ。**ある週の移動平均は、その週のチャンク ＋ **前の週の末尾 6 日**で決まる。
  週チャンクの memo は前週を入力に含める
- **ペース（直近 28 日の回帰）は 4〜5 週を跨ぐ。**窓が固定なので、直近の週だけを入力にすればよい
- **自重種目は体重に依存する。**体重を 1 日直すと、その日以降の有効重量が変わりうる。
  週チャンクの導出は「その週の workouts ＋ その時点の体重の引き当て」を入力にする

### 4.2 移行

**運ぶのは生データだけ**なので、今回（2026-09-05）の IndexedDB 移行と同じ作法で書ける。
1 レコードを読んで週ごとに割り直し、書き終えてから旧レコードを消す。
導出値を運ばないので、移行の途中で「古い計算結果が残る」ことが起こらない。

---

## 5. 本末転倒が構造的に起きない理由

**これがこの設計を選ぶ理由そのもの。**

導出値を保存すると、無効化の条件を**人が書く**ことになる。

| 操作 | 無効になる範囲 |
| --- | --- |
| 過去の日を編集 | その週（自重種目があれば以降の週も） |
| 種目の `rmDivisor` を変更 | 全期間 |
| 補助部位の係数を変更 | 全期間（部位別セット数がすべて変わる） |
| `loadMode` / `bodyweightFactor` を変更 | 全期間 |
| 体重の修正 | 自重種目のある以降の週すべて |

**1 つ書き漏らすと、古い値が正しい顔で表示される。**画面には数字が出るので気づけない。

週で区切るだけなら、無効化は**参照の同一性**で決まる。
ある週の生データが変われば、そのチャンクの参照が変わって memo が外れる。
種目の係数を変えれば `exercises` の参照が変わり、**全週の memo が一斉に外れる**。
書き漏らしようがない。

さらに導出値はメモリ上にしかないので、起動のたびにゼロから作り直される。
**ずれた状態が保存されて残ることが、そもそも起こらない。**

「データが変化したのに再計算されない」を防いでいるのは規律ではなく構造で、
だから `design-training.md` §6.2 を破らずに済む。

## 6. 採らないもの（恒久）

| 採らない | 理由 |
| --- | --- |
| **週サマリ・月サマリの保存** | 導出値の保存そのもの。無効化の条件を人が書くことになり、書き漏らせば古い値が正しい顔で出る（§5）。読み込みは起動時 1 回でボトルネックではないので、払う対価に見合わない |
| 読み込みの局所化（古い週を読まない） | 全期間の数字を出す以上、全期間のデータが要る（§3） |
| 入力の確定を遅らせる（アイドル確定） | 打った直後にアプリを終了されると、値が `AppData` に入る前に失われる。IndexedDB には同期 API が無いので `pagehide` では守れない。**耐久性を削って速さを買わない** |
| 落ちる直前に全体を localStorage へ控える | 上の対策として検討したが、避けたはずの 5 MB の天井を持ち帰る。しかも失敗するのはアプリが落ちる直前で、画面に出せない |
| 導出を Web Worker へ出す | 結果を戻すたびに structured clone が要る。いま重いのはその変換に近いコストなので、移した先で同じものを払う |
| 日単位のレコード | 週で足りる。レコード数が 7 倍（10 年で 3,650）になるぶん、起動時の読み出しが不利になる |

## 7. 段階

| 段階 | 内容 | 状態 |
| --- | --- | --- |
| 0 | 重複計算の除去（§2.1） | **完了**（2026-09-05） |
| 1 | `buildSessions` の `daily` 依存を切る。10 年ぶんで 65 → 17 ms | **未着手。段階 2 をやるなら飛ばす** |
| 2 | 週で区切る（§4） | 未着手 |

段階 1 は増分計算の設計が要るうえ、段階 2 で作り直しになる。
**やるなら段階 1 を飛ばして直接 2** のほうが総量が少ない。

### 着手の合図

**実機で入力が重いと感じたとき。**数字だけを見て先回りしない。
1 年ぶんの実測が 4.8 ms なので、当面その状態は来ない。

判断には `npm run bench` を使う。生成は決定的なので、前後で同じ物差しで比べられる。

## 8. 決定済み

| 項目 | 決定 |
| --- | --- |
| 保存するもの | **生データだけ。導出値は保存しない** |
| 区切る単位 | **週（日曜〜土曜）。**既存の集計単位をそのまま使う |
| 区切る目的 | **書き込みと再計算の局所化。**読み込みの局所化ではない |
| 週に属さないもの | 種目マスタ・プリセット・設定・許容済みは別レコード |
| 導出の置き場所 | **メモリのみ。**起動のたびに作り直す |
| 無効化 | **参照の同一性に任せる。**条件を人が書かない |
| 週サマリ | **持たない**（§6） |
| 読み込み | **起動時に全部読む。**局所化しない |
| 移行 | 生データだけを運ぶ。今回の IndexedDB 移行と同じ作法 |
| 着手の判断 | 実機の体感。物差しは `npm run bench` |
